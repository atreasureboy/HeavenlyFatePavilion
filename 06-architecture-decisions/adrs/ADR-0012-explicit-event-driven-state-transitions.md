# ADR-0012：所有关键状态通过显式事件转换

状态：Accepted

日期：2026-07-24

## 背景

核心对象和跨面契约已经定义，但如果状态改变依赖 Agent 的自然语言结论、工作流内部变量或数据库字段被直接覆盖，退回、失败、争议、更正和回滚就无法形成一致语义。

## 驱动因素

- Agent、Tool、人类和外部事件都可能触发状态变化；
- 事实更正和产品撤回需要向下游传播；
- Failed、Rejected、Cancelled、Degraded 等状态不可混用；
- 状态变化必须可审计、可重放、可解释；
- 能力演进需要可靠的失败和结果证据。

## 候选方案

1. 各组件自行维护状态；
2. 使用通用 status 字段，由调用方直接更新；
3. 为关键对象建立显式状态机，状态只通过有名称的 Event 或 Decision 转换。

## 决定

采用方案 3。

- Mission、Plan、Run、Task、Claim、Fact、Assessment、Forecast、Risk、Alert、Product、Capability Candidate 和 Capability Version 使用显式状态机；
- 转换记录旧状态、新状态、触发者、原因、版本、时间和 trace；
- Agent 可以建议转换，有权服务或治理主体执行转换；
- 更正和争议通过新版本和影响事件传播，不静默覆盖；
- 异常形成结构化 Exception Record，并按类别、严重度和所有面路由；
- S4 异常默认停止相关路径并升级人类，不自动扩大影响范围。

## 影响

正面影响：

- 运行、知识、研判、产品和演进生命周期拥有共同纪律；
- 失败、退回和降级可以被场景验证；
- 更正传播、预测校准和发布回滚获得稳定语义；
- Agent 不能通过一段文本暗中改变权威状态。

代价与风险：

- 状态、事件和转换数量显著增加；
- 分布式转换、一致性和重复事件需要后续技术设计；
- 过细状态机会降低可理解性，应保持业务语义优先；
- 技术进程状态与业务对象状态需要明确映射。

## 重新评估条件

- 状态机复杂度超过其审计和恢复价值；
- 某些对象被证明不需要独立生命周期；
- 未来运行平台提供同等显式、可验证的统一状态语义；
- 场景验证发现现有状态无法表达关键异常或恢复路径。
