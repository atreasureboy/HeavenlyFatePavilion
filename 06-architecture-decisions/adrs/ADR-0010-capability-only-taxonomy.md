# ADR-0010：能力树只按稳定业务能力分类

状态：Accepted

日期：2026-07-24

## 背景

早期二级节点混合了皇帝、三省、官署、对象、服务、存储和处理步骤。混合分类虽然容易讲故事，却会让能力所有权、组件实现和组织映射相互纠缠。

## 驱动因素

- 能力树需要在模型、Agent 和技术实现变化时保持稳定；
- 组织、对象、组件和流程需要能够多对多映射；
- 十个一级面必须使用同一种分类规则；
- Agent / Tool 经济性应当附着于能力，而不是由官职名称决定。

## 候选方案

1. 延续官制组织树作为完整能力树；
2. 混合组织、对象、组件和能力；
3. 能力树只表达“系统能够做什么”，其他视图另行映射。

## 决定

采用方案 3。

- 二级节点只表达稳定能力；
- 组织映射、对象所有权、组件实现、流程顺序和质量属性使用独立视图；
- 每个能力只有一个主要所有面；
- 能力默认标记为 Agent-led、Mixed 或 Tool-led；
- 标记可以随时代和评测变化，但能力契约保持稳定；
- 三省、六部和公共官署在下一步映射到能力节点，不作为能力分类的唯一来源。

## 影响

正面影响：

- 能力骨架不被古代官制或当前技术实现锁死；
- Agent 与 Tool 的替换不会迫使重画业务能力树；
- 重复能力和职责空洞更容易暴露；
- 后续可以分别形成组织图、组件图、对象图和时序图。

代价与风险：

- 官制叙事与技术能力之间多了一层映射；
- 部分能力名称较抽象，需要结合场景和文字图理解；
- “只有一个主要所有面”不意味着只有一个参与面，协作关系仍需契约表达。

## 重新评估条件

- 能力节点无法稳定跨越模型或技术代际；
- 大量能力长期需要多个共同所有者；
- 官署映射证明当前一级面边界与真实能力结构严重冲突；
- 场景验证发现关键能力无法归入任何树。
