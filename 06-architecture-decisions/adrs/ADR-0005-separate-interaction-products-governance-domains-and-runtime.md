# ADR-0005：拆分交互、产品、治理与领域并划定控制运行边界

状态：Accepted

日期：2026-07-24

## 背景

上一版一级骨架将用户交互与情报产品合并，也将朝廷治理与领域协作合并；平台控制面与智能执行运行面虽然并列，但缺少清晰的状态所有权边界。

## 驱动因素

- 一级面必须按同一种职责分类逻辑保持内聚；
- 人机关系与情报交付物拥有不同生命周期；
- 三省治理权与六部专业能力不能因官制类比而混写；
- Agent 模板、策略和配置不能与某次 Run 中的实例状态混为一体。

## 候选方案

1. 保持合并，以减少一级面数量；
2. 拆分交互与产品、治理与领域，同时按控制面和执行面划分长期与即时状态。

## 决定

采用方案 2：

- “用户交互与情报产品面”拆为人机交互面和情报产品面；
- “朝廷治理与领域协作面”拆为智能治理面和领域能力面；
- 平台控制面维护长期期望状态；
- 智能执行与运行面承载具体任务的即时执行状态。

典型归属：

```text
平台控制面
→ Tenant、Policy、Configuration、Model Catalog、Agent Template、Budget、Version

智能执行与运行面
→ Run、Task、Agent Instance、Tool Call、Runtime Context、Execution Event
```

## 影响

正面影响：

- 十个一级面各自回答一种稳定的架构问题；
- 皇帝交互投影、皇帝治理本体、三省和六部获得明确位置；
- 控制面资产可以独立版本化，运行面实例可以独立调度和恢复；
- 后续二级能力树更容易保持类型一致。

代价与风险：

- 一级面数量增至十个，总图需要通过分组和分层保持可读性；
- 情报产品会同时依赖交互、认知、研判和数据底座，需要在关系图中表达而非强塞进职责树；
- 控制状态下发、运行状态回报和配置生效一致性需要后续专题设计。

## 重新评估条件

- 人机交互与情报产品被证明拥有完全相同的所有者和生命周期；
- 三省或六部的正式映射发生根本改变；
- 未来运行范式不再区分模板与实例、期望状态与即时状态。
