# ADR-0007：共享平台承载租户级逻辑朝廷

状态：Accepted

日期：2026-07-24

## 背景

天机阁需要支持不止一位仙人和不止一个仙门。必须确定皇帝、三省六部、租户配置和运行实例究竟是全平台共享、每租户物理复制，还是共享平台上的逻辑隔离。

## 驱动因素

- 每个租户需要独立关系、策略、预算、数据和治理语境；
- 通用采集、模型、Tool、运行和公共资料不应按租户整套复制；
- 皇帝需要稳定身份，但高级模型进程不应因身份稳定而永久常驻；
- 多租户上下文必须能够沿完整执行链传播。

## 候选方案

1. 全平台只有一个共享皇帝和一套共享朝廷；
2. 每个租户物理复制完整天机阁；
3. 共享平台承载每租户独立的逻辑朝廷，运行实例按需创建。

## 决定

采用方案 3：

- 天界平台共享基础设施、通用平台能力、通用模型与工具，以及明确允许共享的公共资料；
- 每个仙门拥有独立 `tenant_id`、Court Profile、皇帝稳定身份、私有覆盖层、预算、策略和审计；
- 皇帝与三省六部具有稳定逻辑身份或能力注册，但运行 Agent 可以按会话、事件或任务创建；
- 皇帝运行实例加载平台基线、Court Profile、皇帝身份、当前用户和 Mission 上下文；
- 长期事实、偏好、决定和审计进入权威存储，不依赖模型上下文永久存在；
- 公共作用域显式建模，不以缺失租户标识暗示共享。

## 影响

正面影响：

- 兼顾租户独立关系与平台规模经济；
- 皇帝可以保持人格和责任连续性，而不浪费常驻推理资源；
- 通用能力升级可以被多个租户共享；
- 私有数据、派生研判和租户意图拥有清晰归属。

代价与风险：

- Court Profile、稳定身份和短期运行实例之间需要精确版本绑定；
- 上下文丢失会造成严重的租户归属错误；
- 公共数据、租户私有覆盖和跨租户协作需要后续更细的作用域模型；
- 平台运营责任与租户数据使用权必须保持分离。

## 重新评估条件

- 未来法规要求某类租户必须物理独占完整平台；
- 皇帝被重新定义为跨租户共享的单一人格；
- 跨租户联合调查成为主形态，单租户逻辑朝廷不再是合适边界；
- 运行模型不再区分稳定身份和短期实例。
