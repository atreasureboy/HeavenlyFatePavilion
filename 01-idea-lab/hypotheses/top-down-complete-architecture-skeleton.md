# 自顶向下的完整架构骨架

状态：Seed

记录日期：2026-07-23

来源：用户提出，Codex 整理

## 问题与观察

天机阁不是准备投入实现的普通产品，也不以尽快交付 MVP 为目标。它是一套用于深入研究和展示系统架构能力的超大型参考架构。

因此，“先设计一个小系统，再随着实现逐步扩展”的产品开发方式未必适合本项目。若从局部实现出发，早期偶然形成的边界可能反过来限制终局设计，使大量跨领域问题直到后期才被发现。

## 核心设想

先定义天机阁终局所需要的完整架构空间，形成稳定的全局骨架，再向各区域持续填充和深化。

这里的“完整”不是预先决定每个技术细节，而是确保所有重要问题都有明确位置、边界和关联关系：

```text
先确定整个系统必须回答哪些问题
→ 为问题建立完整架构地图
→ 对每个区域形成浅层基线
→ 通过端到端场景发现跨域矛盾
→ 选择关键纵切面进行深度设计
→ 将结论反向修正全局骨架
```

这是一种“广度优先建立全貌，深度优先验证关键链路”的方法，而不是 MVP 扩张。

## 架构价值

- 从终局质量属性和系统边界出发，避免实现细节主导架构；
- 提前暴露跨租户、跨权力、跨数据生命周期和跨运行层的问题；
- 允许领域、治理、运行、安全和成本设计从一开始相互引用；
- 适合形成大型、系统化且可用于面试深入追问的架构卷宗；
- 使未来每个新想法都有稳定归属，而不是不断重构文档分类。

## 风险与反面意见

- 终局需求高度假设化，可能产生大量“精确但错误”的设计；
- 缺少实现反馈，组件边界可能只在图上成立；
- 容易追求覆盖面和字数，而失去架构驱动因素；
- 如果所有区域同时深入，概念冲突和维护成本会快速上升；
- 过早选定产品、中间件或部署细节会形成虚假确定性。

## 控制方式

- 使用 `Seed / Draft / Proposed / Accepted` 表达确定性；
- 先固定问题空间和职责边界，不急于固定技术产品；
- 使用标准场景、容量模型、威胁模型和故障推演代替部分实现反馈；
- 每项设计明确假设、适用范围和重新评估条件；
- 采用“全域浅基线＋少数纵向深切面”，避免平均用力；
- 保留候选方案和被否决路径，不制造事后确定性。

## 需要验证的问题

1. 怎样定义“整体骨架已经覆盖完整”？
2. 哪些内容属于稳定骨架，哪些应允许频繁变化？
3. 第一批纵向深切面应选择哪些标准场景？
4. 没有代码和运行数据时，如何证明设计内部可行？
5. 如何防止古代政体和操作系统类比替代真实架构推理？

## 影响区域

- 项目设计方法；
- 文档组织方式；
- v0001 概念基线；
- 当前架构视图；
- 场景和验证体系；
- ADR 与面试呈现方式。
