# G1-A：十面二级逻辑系统候选总树

状态：Draft

形成日期：2026-07-29

来源：G1 十面覆盖审计、现有能力树、平面契约、组织映射、情报语义基线与 Windows W1—W6 候选材料

## 一、本轮目标

本轮只回答：

> 十个一级面内部，分别需要哪些稳定的二级逻辑系统？

本轮不回答：

- 一个逻辑系统由多少服务实现；
- 使用什么数据库、队列、模型或框架；
- 完整 API、事件字段和 Schema；
- Agent 数量、Prompt 与调度算法；
- 物理部署、容量和 SLO；
- 每个系统的完整状态机。

这是一张候选系统树，不是当前生效架构。后续必须经过 G1-B 权威轮、G1-C 连接轮和 G1-D 生存轮，才可能被采纳。

## 二、系统准入测试

不能把每项能力机械改名为“某某系统”。候选逻辑系统至少应具有清晰主责任，并在以下条件中满足两项以上：

1. 拥有与相邻系统不同的权威状态；
2. 拥有独立生命周期；
3. 拥有独立授权、风险或信任边界；
4. 拥有独立伸缩与资源治理模式；
5. 拥有独立失败、恢复或降级边界；
6. 聚合多项必须共同演进的能力；
7. 对上下游提供稳定逻辑契约；
8. 即使未来实现形态变化，其责任仍然存在。

反向排除：

```text
只是一个处理步骤
只是一个对象名称
只是一个 Agent 角色
只是一个数据库或产品名
只是一个横切质量属性
只是为了十面对称
→ 不足以成为逻辑系统
```

## 四、人机交互面候选系统

### IX-01 交互入口与渠道网关

主责任：

- 接收 Web、API、IM、语音、邮件和未来终端输入；
- 完成协议适配、消息规范化、流控和交付回执；
- 将外部交互变成可追踪的内部交互事件。

不负责：

- 判断用户拥有什么权力；
- 解释复杂 Mission；
- 形成情报结论。

成立理由：具有独立渠道生命周期、故障和伸缩边界。

### IX-02 身份与朝廷入口解析系统

主责任：

- 将交互连接解析到 Tenant、Court、Human Actor 和当前 Session；
- 处理登录态、朝廷切换、联合空间入口和身份不确定状态；
- 调用平台控制面的身份权威，而不自行发明身份。

不负责：

- 保存身份与授权策略的权威定义；
- 为请求授予新的业务权力。

成立理由：交互入口的“你是谁、进入哪座朝廷”与渠道协议、治理意图是独立问题。

### IX-03 皇帝体验投影系统

主责任：

- 维持皇帝统一人格、表达风格和全局态势的用户可见投影；
- 将治理状态、产品状态和系统状态组合为连贯体验；
- 管理语言、可访问性、偏好与解释粒度。

不负责：

- 保存皇帝的治理权威状态；
- 绕过三省直接作出治理决定。

成立理由：统一体验需要稳定连续性，但其权力必须与皇帝治理本体分离。

### IX-04 会话与对话连续性系统

主责任：

- 管理 Conversation、Session、Turn、引用、分支、暂停和恢复；
- 保留用户显式表达、上下文选择和对话交付状态；
- 在多个设备和时间跨度间维持可解释连续性。

不负责：

- 将聊天历史作为权威事实库；
- 将会话上下文自动扩散给全部 Agent。

成立理由：具有独立长期状态、并发和恢复问题。

### IX-05 注意力、通知与打断系统

主责任：

- 合并告警、主动通知、任务进展和人类待办；
- 根据紧迫性、注意力预算和渠道条件安排呈现；
- 追踪提醒、忽略、延后和确认。

不负责：

- 判定 Risk 或 Alert 是否成立；
- 因无法送达而静默解除风险。

成立理由：注意力是稀缺资源，拥有独立排队、抑制、升级与送达失败边界。

### IX-06 人类决定与接管控制台

主责任：

- 呈现待批准、封驳分歧、预算申请和高风险行动；
- 接收仙人的批准、否决、暂停、停止和接管操作；
- 展示决定影响范围与当前控制权。

不负责：

- 判断某人是否具有决定权；
- 将交互按钮点击直接写成未经验证的系统状态。

成立理由：人类主权需要独立、不可被对话润色层吞并的控制入口。

## 五、情报产品面候选系统

### PD-01 产品编排系统

主责任：

- 将已批准的 Fact、Assessment、Forecast、Risk 与受众需求编排为 Product；
- 维护产品结构、章节、引用和依赖清单；
- 支撑回答、档案、报告、卷宗和看板等产品类型。

不负责：

- 接受 Fact；
- 将未审核推断升级为正式结论。

### PD-02 版本与渲染系统

主责任：

- 冻结 Product Edition 的信息截点和对象版本；
- 生成文本、图表、PDF、API 视图和多语言 Rendering；
- 保证不同载体引用同一语义版本。

不负责：

- 决定是否发布；
- 修改底层对象以适配版式。

### PD-03 发布生命周期系统

主责任：

- 管理 Draft、Review、Approved、Released、Superseded、Withdrawn 等产品状态；
- 执行发布前置条件和有效治理 Decision；
- 记录 Release 与 Edition 的关系。

不负责：

- 自行作出发布批准；
- 承担渠道送达。

### PD-04 分发与送达系统

主责任：

- 根据受众、作用域和渠道执行 Distribution；
- 跟踪 Delivery、确认、失败、重试和不可达；
- 保留谁在何时获得哪个产品版本。

不负责：

- 扩大接收者可见范围；
- 因渠道成功就宣称接收者理解或采纳。

### PD-05 订阅与告警产品系统

主责任：

- 管理订阅、监测产品、Alert 实例及其更新；
- 将研判触发转为面向特定接收者的告警产品；
- 维护合并、升级、静默、解除和跟踪视图。

不负责：

- 判定底层 Risk；
- 取代注意力系统决定何时打断仙人。

### PD-06 纠正与接收者影响系统

主责任：

- 接收事实撤回、研判更新和产品缺陷影响；
- 计算受影响 Edition、Release、Distribution 与 Delivery；
- 编排 Update、Correction、Withdrawal、Retraction 和接收者通知。

不负责：

- 删除历史版本；
- 自行裁定底层事实是否错误。

## 六、数据认知面候选系统

### CG-01 来源认知与获取规划系统

主责任：

- 发现、理解和评价 Source；
- 形成来源准入、获取范围、频率、完整性与许可要求候选；
- 把“应该获取什么”交给治理和运行。

不负责：

- 保存 Source Policy 的长期权威配置；
- 亲自承担网络采集运行。

### CG-02 内容处理与证据工程系统

主责任：

- 对 Snapshot 执行解析、抽取、清洗、标准化和结构识别；
- 建立 Evidence Anchor、上下文、变换链和 Claim 候选；
- 区分获取缺陷、内容缺失与抽取缺陷。

不负责：

- 把抽取结果直接接受为 Fact；
- 替代原始 Snapshot 保管。

### CG-03 实体身份解析系统

主责任：

- 进行 Mention、Source-local Record、Entity 候选和 Identity Claim 的解析；
- 执行匹配、消歧、合并建议、拆分和重评；
- 保留歧义与可逆映射。

不负责：

- 因名称相同强制合并；
- 越过租户作用域关联私有身份。

### CG-04 关系与事件构建系统

主责任：

- 从证据和已解析实体形成 Relationship、Event 与候选作用关系；
- 区分持续关系、发生事件、状态视图和因果候选；
- 管理跨源、跨域与跨时间关联。

不负责：

- 把时间相邻自动判定为因果；
- 代替研判解释影响。

### CG-05 Diff 与 Change 认知系统

主责任：

- 形成 Content、Extraction、Knowledge 和 World 四类 Diff；
- 识别变化候选、重要性、新颖性和传播范围；
- 将资料变化与世界变化保持分离。

不负责：

- 把任何 Diff 自动接受为现实 Change；
- 直接形成 Forecast。

### CG-06 验证与事实候选系统

主责任：

- 聚合 Evidence、Claim、Proposition、反证与来源权威；
- 形成 Verification Package、Fact Candidate、争议和补证请求；
- 将高争议问题送入治理案件。

不负责：

- 无权接受主体时自行创建 Fact；
- 抹平不同 Authority Domain 的合法差异。

## 七、情报研判面候选系统

### IA-01 Signal 与研判触发系统

主责任：

- 从 Fact、Event、Change 与指标中识别 Signal；
- 管理 Signal 聚合、去重、新颖性与研判触发；
- 将持续监测结果转为明确研判入口。

不负责：

- 把 Signal 当成 Risk；
- 直接通知最终用户。

### IA-02 态势评估系统

主责任：

- 形成当前态势、影响链、替代解释、不确定性与 Dissent；
- 组合跨领域事实并保留证据责任；
- 产生 Assessment 及其修订。

不负责：

- 把 Assessment 写成 Fact；
- 因结论紧迫而跳过反证。

### IA-03 情景与预测系统

主责任：

- 构建 Scenario、关键变量、条件分支、Forecast 与失效条件；
- 定义预测时间窗、结果空间和解析规则；
- 进行趋势、反事实和干预推演。

不负责：

- 宣称未来已经发生；
- 隐藏模型和假设版本。

### IA-04 风险情报系统

主责任：

- 从 Assessment、Scenario 和 Forecast 形成 Risk；
- 管理可能性、影响、暴露、范围、升级和解除判断；
- 追踪风险随世界状态和干预变化。

不负责：

- 自行授权外部行动；
- 将 Mission Operational Risk 与 Intelligence Risk 混写。

### IA-05 建议选项系统

主责任：

- 形成多个 Recommendation Option；
- 表达目标、代价、依赖、风险、可逆性和预期效果；
- 保留“不行动”及替代方案。

不负责：

- 代替仙人或有权主体作出 Decision；
- 将建议自动变为执行 Command。

### IA-06 结果解析与校准系统

主责任：

- 跟踪 Forecast Resolution、风险暴露、建议后果与实际结果；
- 维护评分、校准、干预和不可解析原因；
- 形成研判改进证据。

不负责：

- 直接修改模型或发布新能力；
- 用单一评分抹平情景和因果差异。

## 八、智能治理面候选系统

### GV-01 皇帝治理协调系统

主责任：

- 维持租户级治理议程、全局态势和跨三省协调；
- 将仙人目标、系统状态、分歧和待决定事项统一呈现；
- 保障治理连续性。

不负责：

- 亲自吞并中书、尚书和门下权力；
- 绕过平台强制策略。

### GV-02 Intent 与 Mission 治理系统

主责任：

- 将明确 Intent 形成 Mission 候选；
- 固定目标、作用域、验收、风险、预算和责任边界；
- 管理 Mission 的授权、修订、暂停和关闭。

不负责：

- 设计具体执行 Plan；
- 直接启动未批准 Run。

### GV-03 规划系统

主责任：

- 形成、比较和修订 Plan；
- 拆解目标、依赖、证据要求、资源估算和备选路径；
- 支撑中书规划 Agent 的可追踪工作。

不负责：

- 亲自调度 Worker；
- 自己批准自己的高影响计划。

### GV-04 执行统筹治理系统

主责任：

- 将有效 Plan 编排为跨部、跨能力的执行意图；
- 协调优先级、资源申请、阶段结果和重规划；
- 支撑尚书统筹 Agent。

不负责：

- 替代运行面的确定性 Scheduler；
- 擅自改变 Mission 目标。

### GV-05 审议、反证与封驳系统

主责任：

- 组织独立审核、反证、质量降级和封驳；
- 管理审查 Mandate、Dissent、Review Record 和退回条件；
- 支撑门下审核 Agent。

不负责：

## 十五、六部如何落入系统树

六部不是再增加六组平台系统，而是领域能力面的六个实例：

```text
吏部实例
├── 人物 / 组织领域边界
├── 身份与履历本体
├── 人物来源与证据标准
├── 人物关系研判方法
├── 吏部 Agent / Tool 能力包
└── 人物领域评测

户部、礼部、兵部、刑部、工部
→ 使用同一 DM-01～DM-06 模板

跨部联合任务
→ DM-07 组织领域协作
→ GV-04 负责治理统筹
→ RT 系统负责实际执行
→ DF 系统负责共同对象保管
```

这保留六部专业自治，同时避免六套重复 Runtime、数据底座和平台控制。

一个官署可以映射多个系统；一个系统也可支撑多个官署。官署表达职责和权力，系统表达稳定逻辑责任。

## 十七、系统树的完整性初检

### 17.1 十面覆盖

- 十面均拥有 6—8 个候选逻辑系统；
- 每个能力树节点均可挂入至少一个候选系统；
- 没有新增第十一个一级面；
- 基础设施保持共同承载。

### 17.2 核心分离

候选总树保持：

```text
交互投影 ≠ 皇帝治理
产品编排 ≠ 发布决定 ≠ 分发送达
认知形成 ≠ 数据保管
事实候选 ≠ 事实接受
研判 ≠ 建议 ≠ 人类决定
领域能力 ≠ 治理统筹 ≠ 运行执行
期望状态 ≠ 实际状态
评测执行 ≠ 演进采用 ≠ 配置发布
```

### 17.3 当前未证明

本轮尚未证明：

- 70 个候选是否都具有独立权威状态；
- 是否存在应合并或拆分的系统；
- 七条全局流在系统之间是否无断链；
- 正常和异常路径是否可闭合；
- 横切约束是否能投影到每个系统；
- 组织角色与系统的全部责任分配是否无冲突。

这些分别属于 G1-B、G1-C 与 G1-D。

## 十八、下一轮：G1-B 权威轮

G1-B 不会一次写 70 份详细设计，而是先为每个系统补四项最小权威标记：

```text
Primary Responsibility
Authoritative State
Decision / Enforcement Authority
Explicit Non-responsibility
```

同时执行合并测试：

```text
若两个候选拥有同一权威状态、相同生命周期、
相同失败边界且总是共同变化
→ 合并候选

若一个候选同时拥有互相制衡的决定权
或两类明显独立生命周期
→ 拆分候选
```

G1-B 完成后，候选数量可以变化，不能为了保留漂亮的 `70` 而拒绝修正。
