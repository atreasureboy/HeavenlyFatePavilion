# 阶段 1：整体架构骨架访谈

状态：Draft

启动日期：2026-07-24

## 一、阶段目标

当前第一阶段只建立天机阁的整体架构骨架。

本阶段采用从整体到局部的方式，先确定：

- 根节点；
- 一级架构面；
- 二级能力域；
- 各架构面之间的基本关系；
- 哪些概念是层级节点；
- 哪些概念是贯穿全局的横切维度；
- 后续每个局部专题应该挂在哪里。

本阶段不深入：

- 越权和授权细节；
- 安全策略；
- Agent 状态机；
- 数据库选型；
- 消息协议；
- Token 计算公式；
- 单个官署的内部设计；
- 故障恢复算法。

这些内容必须先在整体骨架中获得位置，之后再分别展开。

## 二、第一阶段完成物

### 整体架构根图

从天机阁根节点展开到一级架构面和二级能力域。

### 视图规则

明确：

- 树用于表达什么；
- 分层图用于表达什么；
- 横切矩阵用于表达什么；
- 数据流和控制流如何单独表达。

### 顶层关系

至少说明：

- 用户需求如何进入系统；
- 情报生产如何运转；
- 三省六部治理作用于什么对象；
- 天机阁自身智能执行与运行系统承载什么；
- 数据底座保存什么；
- 多租户如何贯穿；
- 最终结果如何输出。

### 局部专题索引

后续任何设计问题都能放入一个明确的一级或二级节点，不需要临时创造新的顶层分类。

## 三、当前已接受一级骨架

经过四轮访谈，一级逻辑骨架确定为：

```text
天机阁
├── 人机交互面
│   └── 皇帝交互投影
├── 情报产品面
├── 数据认知面
│   ├── 掌数
│   ├── 联结
│   └── 察变
├── 情报研判面
│   ├── 推势
│   ├── 卜算
│   └── 警险
├── 智能治理面
│   ├── 皇帝智能中枢本体
│   └── 三省与治理官署
├── 领域能力面
│   └── 六部与专业官署
├── 智能执行与运行面
├── 数据底座面
├── 平台控制面
└── 能力演进面
│   ├── 自主演进
│   └── 人类主导演进

共同承载底座：基础设施
```

当前横切维度：

```text
多租户
身份与权限
证据与血缘
预算与资源
风险与质量
审计与追踪
数据生命周期
```

三省六部采用混合结构；AgentOS 降为外部参考；不同性质的用户关系、产品、认知、研判、治理、领域、运行、数据、控制和演进职责不再混放。

## 四、第一轮访谈结论

### 4.1 情报生产主干

简单的收集、清洗、整理、分配和管理并不完整。候选主干修订为：

```text
需求 / 目标
→ 掌数
→ 联结
→ 察变
→ 推势
→ 卜算
→ 警险
→ 情报产品
→ 反馈
```

其中每个智能阶段都可以反向触发新的收集、关联和验证，因此正式视图应当是闭环而非单向 ETL。

### 4.2 三省六部的位置

采用混合结构：

- 皇帝和三省是治理与统筹层；
- 六部是专业领域层；
- 公共官署按照职责分布到数据、运行、控制、验证和产品区域。

### 4.3 一级架构面

原五面骨架不足，至少需要拆出：

- 数据与情报智能面；
- 朝廷治理与领域协作面；
- 智能执行与运行面；
- 数据底座面；
- 自我迭代面。

是否保留独立基础设施面仍待下一轮确认。

### 4.4 智能运行、能力演进与多租户

当前回答：

- AgentOS 是另一个项目的参考，不属于天机阁当前逻辑架构；
- 天机阁需要独立的智能执行与运行面；
- 天机阁需要独立的能力演进面；
- 演进范围覆盖模型、Agent、Tool、Skill、Workflow、数据语义、来源、评测、组织职责和架构本身；
- 能力演进同时包含系统自主演进和人类主导演进，自主程度可以随时代变化，但可演进性不可缺失。

多租户正式采用双重表达：

- 租户注册、成员、配置、策略、配额、预算和生命周期属于平台控制面的多租户控制子域；
- 租户上下文、数据边界、身份边界、策略边界和预算边界贯穿所有架构面；
- 多租户不是独立一级业务面。

## 五、第二轮访谈结论

### 5.1 两个一级智能面

正式拆分为：

```text
数据认知面：掌数、联结、察变
情报研判面：推势、卜算、警险
```

前者负责形成可理解、可关联、可追踪变化的世界状态，后者负责基于该状态形成态势、未来和风险判断。两者构成反馈闭环，不是不可逆的单向流水线。

### 5.2 全域能力演进

任何不能跟随 Agent、模型和智能系统范式持续变化的天机阁架构，最终都会失去时代适配性。因此演进对象是全部系统能力，而不是模型和 Agent 的局部更新。

系统能够自行观察、提出、实验和验证的部分属于自主演进；尚不具备自主演进能力的部分，由人类持续设计和升级。二者共同归入能力演进面。

### 5.3 多租户双重表达

多租户不与业务能力争夺一级面位置。它一方面具有集中控制职责，另一方面要求租户上下文沿请求、任务、数据、索引、缓存、事件、模型调用和情报产品全链路传播。

## 六、第三轮访谈结论

### 6.1 皇帝是具身化智能中枢

皇帝不是普通聊天入口或单纯任务路由器，其系统形态类似红后、EVA、贾维斯式的统一智能中枢：以一个持续、完整的人格代表整座天机阁与仙人交互，理解全局态势，协调内部能力，并主动汇报和告警。

架构上采用双重表达：

- 皇帝智能中枢本体属于智能治理面；
- 皇帝在人机交互面形成统一交互投影；
- 本体与投影是同一逻辑主体的两个视图；
- 皇帝通过三省六部和运行系统协调能力，不亲自承担全部执行。

### 6.2 数据底座独立

数据底座保持独立一级架构面。它负责持久化、组织、版本化和供应原始资料、证据、事实、关系、变化、研判与风险记录，不与负责理解数据的数据认知面或负责执行 Agent 的运行面合并。

### 6.3 基础设施降为共同承载底座

基础设施不作为一级逻辑能力面。它位于顶层逻辑骨架下方，为全部架构面提供计算、存储、网络、队列、部署和容灾承载；在部署架构和物理架构中再展开。

## 七、第四轮访谈结论

### 7.1 人机交互与情报产品拆分

- 人机交互面负责仙人如何与天机阁建立持续关系，包括皇帝交互投影、对话、多模态入口、主动通知和反馈；
- 情报产品面负责天机阁交付什么，包括档案、图谱、时间线、报告、趋势、情景和风险告警。

### 7.2 智能治理与领域能力拆分

- 智能治理面负责任务如何被规划、统筹、审核、封驳和问责，容纳皇帝本体、三省及治理型官署；
- 领域能力面负责系统具备哪些专业知识与业务能力，容纳六部及领域型官署；
- 三省是治理权力，六部是专业能力，二者不再因官制类比而被强行放入同一职责面。

### 7.3 平台控制与智能运行划界

```text
平台控制面：维护系统长期期望状态
智能执行与运行面：承载任务即时执行状态
```

平台控制面管理租户、配置、策略、模型目录、Agent 模板、预算和版本。智能执行与运行面管理 Run、Task、Agent 实例、Tool 调用、调度、上下文和故障恢复。
