# 阶段 1：整体架构骨架访谈

状态：Draft

启动日期：2026-07-24

## 一、阶段目标

当前第一阶段只建立天机阁的整体架构骨架。

本阶段采用从整体到局部的方式，先确定：

- 根节点；
- 一级架构面；
- 二级能力域；
- 各架构面之间的基本关系；
- 哪些概念是层级节点；
- 哪些概念是贯穿全局的横切维度；
- 后续每个局部专题应该挂在哪里。

本阶段不深入：

- 越权和授权细节；
- 安全策略；
- Agent 状态机；
- 数据库选型；
- 消息协议；
- Token 计算公式；
- 单个官署的内部设计；
- 故障恢复算法。

这些内容必须先在整体骨架中获得位置，之后再分别展开。

## 二、第一阶段完成物

### 整体架构根图

从天机阁根节点展开到一级架构面和二级能力域。

### 视图规则

明确：

- 树用于表达什么；
- 分层图用于表达什么；
- 横切矩阵用于表达什么；
- 数据流和控制流如何单独表达。

### 顶层关系

至少说明：

- 用户需求如何进入系统；
- 情报生产如何运转；
- 三省六部治理作用于什么对象；
- 天机阁自身智能执行与运行系统承载什么；
- 数据底座保存什么；
- 多租户如何贯穿；
- 最终结果如何输出。

### 局部专题索引

后续任何设计问题都能放入一个明确的一级或二级节点，不需要临时创造新的顶层分类。

## 三、当前候选一级骨架

第一轮访谈后，候选骨架修订为：

```text
天机阁
├── 用户交互与情报产品面
├── 数据与情报智能面
│   ├── 掌数
│   ├── 联结
│   ├── 察变
│   ├── 推势
│   ├── 卜算
│   └── 警险
├── 朝廷治理与领域协作面
├── 智能执行与运行面
├── 数据底座面
├── 平台控制面
├── 自我迭代面
└── 基础设施面
```

候选横切维度：

```text
多租户
身份与权限
证据与血缘
预算与资源
风险与质量
审计与追踪
数据生命周期
```

三省六部采用混合结构；AgentOS 降为外部参考；关联、察变、推势、卜算和警险从普通数据处理或产品能力提升为情报智能能力；自我迭代成为独立一级面。

## 四、第一轮访谈结论

### 4.1 情报生产主干

简单的收集、清洗、整理、分配和管理并不完整。候选主干修订为：

```text
需求 / 目标
→ 掌数
→ 联结
→ 察变
→ 推势
→ 卜算
→ 警险
→ 情报产品
→ 反馈
```

其中每个智能阶段都可以反向触发新的收集、关联和验证，因此正式视图应当是闭环而非单向 ETL。

### 4.2 三省六部的位置

采用混合结构：

- 皇帝和三省是治理与统筹层；
- 六部是专业领域层；
- 公共官署按照职责分布到数据、运行、控制、验证和产品区域。

### 4.3 一级架构面

原五面骨架不足，至少需要拆出：

- 数据与情报智能面；
- 朝廷治理与领域协作面；
- 智能执行与运行面；
- 数据底座面；
- 自我迭代面。

是否保留独立基础设施面仍待下一轮确认。

### 4.4 智能运行、自我迭代与多租户

当前回答：

- AgentOS 是另一个项目的参考，不属于天机阁当前逻辑架构；
- 天机阁需要独立的智能执行与运行面；
- 天机阁需要新增独立的自我迭代面。

多租户应当是：

- 一个独立一级分支；
- 平台控制面的子能力；
- 贯穿所有架构面的横切维度；
- 同时具有控制面和横切属性。

多租户的位置仍待回答。

## 五、第二轮访谈问题

### 问题 1：六项智能能力的层级

掌数、联结、察变、推势、卜算、警险应该：

- 共同作为“数据与情报智能面”的六个二级能力；
- 各自成为一级架构面；
- 掌数和联结属于数据面，察变、推势、卜算、警险属于研判面；
- 使用其他分法。

### 问题 2：数据底座是否独立

原始资料、事实、证据、图谱、变化历史、时间线、预测和风险记录规模极大。数据底座应该：

- 独立成为一级架构面；
- 放入数据与情报智能面；
- 与智能执行合并为运行与数据面。

### 问题 3：自我迭代面的覆盖范围

自我迭代面是否应该同时覆盖：

- 模型；
- Agent；
- Tool、Skill 和 Workflow；
- 领域本体和数据 Schema；
- 来源和采集器；
- 评测和验证体系；
- 三省六部组织与职责。

还是只负责模型和 Agent 能力更新？

### 问题 4：基础设施与多租户的位置

基础设施是否需要出现在一级逻辑骨架中，还是只在部署架构中出现？

多租户应该：

- 独立一级面；
- 平台控制面子域；
- 全局横切维度；
- 同时是控制面子域和全局横切维度。
