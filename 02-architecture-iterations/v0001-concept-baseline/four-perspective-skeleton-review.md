# 四视角架构骨架修复评审

状态：Proposed

记录日期：2026-07-24

所属迭代：v0001 概念基线

## 一、评审目标

现有 v0001 骨架已经初步建立“仙人—皇帝—三省—六部—公共官署”的治理体系，以及 Agent / Tool 的分配原则。

本次评审从四个此前没有被同时放到中心位置的视角检查骨架：

1. 实际业务：天机阁如何完成数据收集、清洗、整理、分配和管理；
2. Agent：Agent 应放在哪里，如何节省 Token 又不损害功能；
3. 宏观架构：如何从顶点逐级分解，生长出完整骨架；
4. 多租户与用户：不同需求如何改变系统行为和产品形态。

本次评审的目标不是替换三省六部，而是给官制治理模型补上业务主干、经济模型、分解方法和需求模型。

## 二、第一项修复：从实际业务重新定义天机阁

### 2.1 候选定义

从用户直觉看，天机阁可以被描述为一个负责数据收集、清洗、整理、分配和管理的超大型 Agent。

从正式架构语义看，更准确的定义是：

> 天机阁是一套超大型 Agentic Intelligence System。它以确定性数据工业体系为主体，以少数 Agent 作为高不确定性决策层，将合法数据持续转化为可验证、可分配、可管理并面向不同租户交付的情报产品。

不宜把整个系统形式化为“一个大 Agent”，原因是：

- 数据库、抓取器、索引、队列和规则引擎不是 Agent 的内部思维；
- 海量数据生命周期必须脱离单次 Agent 上下文长期存在；
- 多租户隔离不能依赖一个 Agent 记住边界；
- 事实一致性、权限和审计必须由确定性系统强制；
- 系统可以在没有高级 Agent 运行时持续采集、清洗和监测。

因此可以保留“天机阁是一个超大型 Agent”的产品叙事，但技术定义必须是“Agent 化情报系统”。

### 2.2 五段业务主链

```text
数据收集
→ 数据清洗
→ 数据整理
→ 数据分配
→ 数据管理
```

五段不是简单 ETL，它们共同构成情报生产闭环。

### 2.3 数据收集

#### 目标

持续获得合法、可追溯、与用户目标相关的原始资料。

#### 能力

- 来源发现；
- 来源准入和许可检查；
- 网页、RSS、API、文件和消息接入；
- 定时采集和事件触发采集；
- 原始快照；
- 内容 Hash；
- 抓取时间和发布时间记录；
- 来源健康监控；
- 重试、限速和失效处理。

#### 主要承担者

- 工部采集 Tool；
- 文渊阁；
- 钦天监；
- 通政司；
- 来源准入策略。

#### Agent 介入点

- 发现新来源；
- 为复杂任务制定采集策略；
- 判断未知页面或数据源的语义价值；
- 处理规则未覆盖的来源许可疑问。

大规模正常采集不由 Agent 执行。

### 2.4 数据清洗

#### 目标

将异构、噪声和不完整资料转化为可继续处理的标准内容。

#### 能力

- 格式识别；
- 正文抽取；
- OCR；
- 编码和语言识别；
- 去广告和模板噪声；
- URL、文档和近似内容去重；
- 字段标准化；
- 时间、单位和名称规范化；
- 恶意内容隔离；
- 清洗质量检查。

#### 主要承担者

- 工部解析 Tool；
- 专用模型；
- 清洗 Worker；
- 规则和质量检测服务。

#### Agent 介入点

- 复杂版面和语义结构无法确定；
- 多种解析结果相互冲突；
- 文档具有特殊领域格式；
- 需要生成新的解析方案。

清洗不应把原始资料覆盖掉。文渊阁保存原件，清洗结果是带版本和血缘的派生物。

### 2.5 数据整理

#### 目标

把内容转化为实体、证据、主张、事实、事件、关系、时间线和信号。

#### 能力

- 实体和关系抽取；
- 身份候选生成；
- 实体消歧和合并；
- Evidence 定位；
- Claim 生成；
- 事件聚类；
- 时间线构建；
- 事实版本和双时态；
- 来源独立性分析；
- 冲突检测；
- 推断与事实分层。

#### 主要承担者

- 吏部、礼部、兵部、刑部等领域 Tool；
- 国史馆；
- 大理寺；
- 规则引擎和专用模型。

#### Agent 介入点

- 同名身份存在高歧义；
- 多来源事实冲突；
- 需要跨领域建立关系；
- 需要解释事件含义；
- 需要形成高层研判。

这是 Tool 与 Agent 最重要的交界面之一。

### 2.6 数据分配

“分配”不能只理解为把任务交给六部。至少存在四种分配：

#### 领域分配

决定材料或任务属于吏部、户部、礼部、兵部、刑部或多个部门。

#### 存储分配

决定原件、索引、事实、关系、向量、时序指标和审计记录分别进入哪个逻辑数据系统。

#### 权限分配

决定内容属于公共域、租户私有域、用户私有域、联合调查域还是受限域。

#### 产品分配

决定哪些用户、订阅、专题、告警渠道和报告可以接收结果。

正常分配应由路由规则、策略引擎、订阅匹配和索引服务完成。只有出现语义歧义、跨域争议、敏感边界或优先级冲突时才升级给 Agent。

### 2.7 数据管理

#### 目标

在完整生命周期中保持数据的质量、合法性、可追溯性、可访问性和可删除性。

#### 能力

- 权威所有者；
- 版本和有效时间；
- 来源和证据血缘；
- 数据质量等级；
- 租户隔离；
- 访问策略；
- 保留期限；
- 删除和派生删除；
- 纠错；
- 归档；
- 备份与恢复；
- 审计；
- 成本和容量治理。

数据管理不是业务链末尾的一次动作，而是贯穿收集、清洗、整理和分配的横切控制。

### 2.8 闭环补充

五段业务链还需要两个端点：

```text
用户意图 / 监测目标
        ↓
收集 → 清洗 → 整理 → 分配 → 管理
        ↓
情报产品 / 用户反馈 / 新监测目标
        └───────────────────────↺
```

没有用户意图，系统会沦为无边界的数据囤积；没有反馈，系统无法修正来源、质量、排序和产品价值。

## 三、第二项修复：Agent 放置与 Token 经济性

### 3.1 Agent 应放在不确定性边界

Agent 不按照组织图平均分配，也不因为一个节点名称是“尚书”就必然每次运行。

Agent 最适合放在以下边界：

- 意图不明确；
- 路径需要规划；
- 多个领域需要综合；
- 规则无法覆盖；
- 来源互相冲突；
- 结论需要反证；
- 风险和价值需要权衡；
- 结果需要面向用户解释。

可以将 Agent 调用理解为一种昂贵的“认知中断”：

```text
确定性流水线正常运行
→ 检测到歧义、冲突、未知或高风险
→ 产生结构化认知中断
→ Agent 在受限上下文中处理
→ 输出结构化决定
→ 确定性流水线继续运行
```

### 3.2 各阶段的默认执行者

| 业务阶段 | 默认执行者 | Agent 介入条件 |
|---|---|---|
| 来源发现 | 规则、目录、监测 Tool | 新领域、未知来源、复杂价值判断 |
| 数据采集 | Collector / Worker | 采集策略需要动态规划 |
| 数据清洗 | Parser、规则、专用模型 | 格式或语义无法稳定解析 |
| 实体抽取 | 专用模型、规则 | 高歧义身份和跨域关系 |
| Claim 生成 | 结构化抽取模型 | 复杂主张或隐含语义 |
| 事实验证 | 规则、来源评分 | 冲突、反证、高风险结论 |
| 领域路由 | 分类器、策略引擎 | 多领域争议和敏感边界 |
| 产品生成 | 模板、结构化渲染 | 综合研判和复杂解释 |
| 数据治理 | IAM、Policy、生命周期服务 | 新型风险和规则空白 |

### 3.3 不影响功能的 Token 优化原则

Token 优化不能以减少功能、证据或审核为代价。优化对象应是执行方式，而不是业务语义。

候选不变量：

> Token 优化可以改变由谁执行、何时执行和看到多少上下文，但不能降低任务已经承诺的验收条件、权限约束、证据标准和审计要求。

### 3.4 Token 节省机制

#### 确定性优先

优先级：

```text
缓存 / 已验证事实
→ SQL / Search / Graph Query
→ Script / Rule
→ 专用模型 / 小模型
→ 领域 Agent
→ 三省高级 Agent
→ 人类专家
```

#### 按风险升级

低风险、结构化、已有答案的任务不启动完整三省链。高风险、跨域和证据冲突任务才提升验证强度。

#### 上下文按引用装配

Agent 不直接读取整个数据库，只接收：

- 任务目标；
- 验收条件；
- 已授权的数据引用；
- 检索出的最小证据集；
- 工具结构化结果；
- 预算和剩余时间；
- 允许执行的下一步。

原始资料通过 Evidence ID 按需展开，而不是全部复制进上下文。

#### 共享处理，隔离判断

公开资料的采集、清洗、实体抽取和公共事实验证可以跨租户共享一次；租户关注、私有材料、派生研判和产品排序保持隔离。

#### 缓存和中间产物复用

- Prompt 缓存；
- 语义查询缓存；
- 已验证 Claim；
- 实体解析结果；
- 文档摘要和结构化抽取；
- 领域 Tool 结果；
- 审核结果；
- 报告模板。

缓存必须携带版本、租户边界、权限范围和失效条件。

#### 模型分层

- L0：程序和规则；
- L1：分类、NER、Embedding 等专用模型；
- L2：低成本通用模型；
- L3：领域和三省高级模型；
- L4：人工专家。

#### 批处理和异步化

非交互式采集、清洗、抽取、聚类和监测任务优先批处理；交互式 Agent 只处理用户当前需要的部分。

#### 结构化通信

Agent 之间传递计划、证据引用、决议和错误，不进行无目标的自由聊天。

#### 停止条件

每个调查必须包含：

- 最大调用深度；
- 最大 Agent 数量；
- Token 预算；
- 时间预算；
- 证据满足条件；
- 收益递减条件；
- 部分结果返回策略。

### 3.5 保证功能不受损的补偿机制

- 低成本路径未达到验收条件时自动升级；
- Tool 置信度不足时触发 Agent；
- 关键结论始终经过对应风险等级的验证；
- 降级时明确标注证据和结论等级；
- 预算不足时返回部分结果而不是伪造完整性；
- 所有跳过的 Agent 阶段留下原因；
- 用户可以为重要任务提高预算和证据要求。

## 四、第三项修复：从顶点逐级生长架构

### 4.1 树形分解的价值

天机阁需要从最高目的开始，逐层回答：

```text
为什么存在
→ 为谁服务
→ 提供什么价值
→ 必须完成哪些业务能力
→ 由哪些权力和领域承担
→ 依赖哪些运行与数据能力
→ 需要哪些基础设施
```

这种方式可以像树一样从根向下生长，防止直接从六部或数据库开始堆组件。

### 4.2 不应强制成为严格二叉树

“像二叉树”适合表达逐层细分，但不应要求每个节点只能有两个子节点。严格二叉化会制造没有业务意义的中间概念。

候选表达原则：

- 用树表达职责分解和所有权；
- 用有向图表达调用、数据流和依赖；
- 用矩阵表达跨租户、安全、成本和质量等横切关系；
- 用状态机表达生命周期；
- 用时序图表达具体场景。

### 4.3 第一版宏观树

```text
天机阁
├── 用户价值面
│   ├── 主动调查
│   ├── 持续监测
│   ├── 情报产品
│   └── 反馈与协作
│
├── 情报生产面
│   ├── 数据收集
│   ├── 数据清洗
│   ├── 数据整理
│   ├── 数据分配
│   └── 数据管理
│
├── 智能治理面
│   ├── 皇帝
│   ├── 三省
│   ├── 六部
│   └── 公共官署
│
├── 运行与数据面
│   ├── AgentOS
│   ├── Tool / Skill / Worker
│   ├── 数据系统与索引
│   ├── 队列与调度
│   └── 模型与算力
│
└── 平台控制面
    ├── 多租户与身份
    ├── 权限与安全
    ├── 预算与成本
    ├── 质量与审计
    └── 可观测与运维
```

### 4.4 横切维度

以下内容不能只挂在树上的一个分支，它们必须贯穿所有层：

- `tenant_id` 和主体身份；
- 权限与委托链；
- 数据来源和证据血缘；
- 预算和资源消耗；
- 风险等级；
- 审计和追踪；
- 数据生命周期；
- 质量属性；
- 合规和地域边界。

### 4.5 逐层填充方法

每个树节点逐步达到以下深度：

1. 目的；
2. 职责；
3. 非职责；
4. 输入和输出；
5. 权威状态；
6. 上下游关系；
7. 正常流程；
8. 异常流程；
9. 权限、预算和审计；
10. 容量、故障和重新评估条件。

## 五、第四项修复：多租户与用户需求驱动

### 5.1 租户不等于用户

```text
天界平台
└── 仙门 Tenant
    ├── Tenant Owner
    ├── Tenant Admin
    ├── Analyst
    ├── Ordinary User
    └── Guest / External Collaborator
```

一个租户可以有多个用户；同一用户在不同租户中可以拥有不同身份。

### 5.2 用户需求的八个维度

每次调查或监测需求至少可以从八个维度描述：

1. 目标对象：人物、企业、项目、事件、技术、地区或主题；
2. 任务类型：查询、调查、监测、比较、预警或报告；
3. 时间要求：实时、近实时、周期性或历史回溯；
4. 证据要求：概览、标准、严格或专家级；
5. 风险等级：普通、敏感、高风险或受监管；
6. 输出形式：回答、时间线、图谱、简报、告警、API 或专题报告；
7. 资源约束：Token、费用、延迟和最大调查范围；
8. 数据范围：公共数据、租户私有数据、用户私有数据或联合空间。

### 5.3 需求如何改变系统偏向

需求不应改变公共事实本身，但可以改变：

- 调查计划；
- 调用的六部；
- 数据源优先级；
- 新鲜度要求；
- 检索深度；
- 模型等级；
- 审核强度；
- 预算分配；
- 产品排序；
- 报告语言和粒度；
- 推送渠道和频率。

例如：

| 用户需求 | 系统偏向 |
|---|---|
| 快速了解某公司 | 优先公共事实库、缓存和模板，少用高级 Agent |
| 投资前尽调 | 加强户部、吏部、刑部和门下验证 |
| 地缘风险监测 | 加强兵部、钦天监、时效性和预警 |
| 人物观点变化 | 加强礼部、时间线和来源独立性 |
| 法规影响评估 | 加强刑部、规则版本和人工升级条件 |
| 私有竞争情报 | 加强租户隔离、私有覆盖层和访问审计 |

### 5.4 多租户数据分层

```text
全球公共资料与事实底座
        │
        ├── 仙门 A 私有覆盖层
        │   └── 用户个人工作空间
        │
        ├── 仙门 B 私有覆盖层
        │   └── 用户个人工作空间
        │
        └── 临时联合调查空间
```

#### 可以共享

- 合法公开资料采集结果；
- 公共实体身份；
- 公共 Evidence 和已验证事实；
- 来源信誉；
- 通用抽取和清洗结果。

#### 默认隔离

- 租户关注目标；
- 私有来源和上传材料；
- 查询意图和调查历史；
- Agent Memory；
- 私有标签、笔记和评分；
- 派生研判；
- 报告；
- Tool 凭证；
- 预算、策略和审计记录。

### 5.5 租户朝廷画像

每个仙门拥有逻辑朝廷配置，而不是一套物理复制系统：

```text
Court Profile
=
租户身份与成员
+ 关注领域
+ 允许的数据源
+ 私有数据范围
+ Agent 和 Tool 授权
+ 风险政策
+ 证据标准
+ 模型和预算策略
+ 输出渠道
+ 租户记忆
```

皇帝和三省按请求实例化时加载 Court Profile，并继续叠加当前用户身份和任务上下文。

### 5.6 需求驱动但事实中立

候选不变量：

> 用户需求可以改变调查范围、证据深度、研判视角和产品表达，但不能改变公共事实的身份、来源、证据和验证状态。

同一公共事实可以被多个租户用于不同目的，但租户的关注、推断、排序和决策默认私有。

## 六、四视角合并后的修复骨架

```text
仙人 / 用户需求
        │
        ▼
租户朝廷画像 + 当前用户权限 + 任务约束
        │
        ▼
皇帝与三省：理解、规划、执行统筹、审核
        │
        ▼
情报生产主链
收集 → 清洗 → 整理 → 分配 → 管理
        │
        ├── 正常路径：Tool / Script / Worker / Rule / 小模型
        └── 认知中断：部级 Agent / 三省 Agent / 人类
        │
        ▼
公共事实底座 + 租户私有覆盖层
        │
        ▼
按需求生成查询结果、监测、告警和情报产品
        │
        ▼
用户反馈反向更新关注、规则、来源和调查目标
```

## 七、对现有骨架的修复结论

### 保留

- 仙人、皇帝、三省、六部和公共官署；
- 少数高级 Agent 与大量确定性百官；
- 三省权力分立；
- 公共事实底座和租户私有覆盖层；
- AgentOS 作为运行基座；
- 全域骨架先行、局部深度迭代。

### 补强

- 把数据业务生命周期提升为与官制治理同等重要的主干；
- 将“数据分配”明确为领域、存储、权限和产品四种分配；
- 将 Agent 定位为不确定性边界上的认知处理者；
- 建立 Token 优化不降低验收条件的约束；
- 将宏观树、依赖图、矩阵、状态机和场景图分工；
- 将租户朝廷画像和八维用户需求纳入任务上下文；
- 建立需求驱动但事实中立的边界。

### 暂不裁定

- 三省是否每个任务都必须实例化；
- 皇帝是否可以对低风险查询直接使用已验证事实回答；
- “数据分配”是否应成为独立领域上下文；
- 公共事实验证成本如何跨租户分摊；
- Court Profile 中哪些配置可以由用户自行修改；
- 哪些 Agent 跳过策略可以由租户覆盖。

## 八、候选不变量

- 天机阁是 Agent 化情报系统，不是单一模型上下文中的超级 Agent；
- 数据生命周期可以在没有高级 Agent 运行时持续运转；
- Agent 优先处理歧义、规划、冲突、反证、跨域综合和高风险判断；
- Token 优化不能降低已承诺的功能、证据、权限和审核标准；
- 原始资料、派生数据、事实和研判必须分层；
- 数据分配必须同时考虑领域、存储、权限和产品；
- 树表达职责分解，图表达关系，矩阵表达横切关注点；
- 用户需求可以改变调查与表达，不能篡改公共事实；
- 公共处理可以共享，租户意图、私有数据和派生判断默认隔离；
- 每次调用都必须传播租户、主体、权限、预算、风险和追踪上下文。
