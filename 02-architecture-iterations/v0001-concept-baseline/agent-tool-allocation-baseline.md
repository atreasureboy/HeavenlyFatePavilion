# Agent / Tool 职责分配基础骨架

状态：Draft

记录日期：2026-07-23

所属迭代：v0001 概念基线

## 一、目标

本文件建立天机阁第一版 Agent、Tool、Script、Service、Database 和 Policy Engine 的职责分配骨架。

本骨架采用以下总体结构：

> 皇帝主 Agent + 三省核心子 Agent + 六部混合部门（部级 Agent + 工具群）+ 公共官署服务层。

高层规划、执行统筹、独立审核和领域综合判断由 Agent 承担；高吞吐、可重复、可结构化和可确定执行的工作由 Tool、Script、小模型、Worker、数据库和系统服务承担。

本文件是 v0001 的基础迭代骨架，不等于最终架构。具体边界仍需通过场景、状态机、权限模型、成本模型和故障推演验证。

## 二、总裁定原则

### 2.1 适合使用子 Agent 的工作

当一项职责同时或显著具备以下特征时，优先考虑由 Agent 承担：

- 需要理解开放式目标；
- 需要制定或修订计划；
- 需要跨领域综合判断；
- 需要多步骤决策；
- 需要在信息不足时选择调查路径；
- 需要反证、审核或争议裁定；
- 需要综合多个来源形成解释性结论；
- 需要在多个合理方案之间权衡。

在官制类比中，这类职责通常对应：

- 高层大臣；
- 三省主官；
- 部级主官；
- 复杂调查官；
- 高风险审核或裁定官。

### 2.2 适合使用 Script / Tool 的工作

当一项职责具备以下特征时，优先使用确定性组件：

- 确定性强；
- 重复频率高；
- 吞吐量大；
- 输入输出结构化；
- 不需要复杂推理；
- 可以由程序、规则、索引或专用模型稳定执行；
- 需要严格复现、低延迟或精确计量。

在官制类比中，这类职责通常对应：

- 绝大多数小官和属官；
- 胥吏；
- 账房；
- 档案官；
- 执行固定制度的基层机构。

### 2.3 形态不由官位名称自动决定

官署是逻辑职责边界，不等于一个大模型进程。一个官署可以由以下任意组合构成：

```text
Agent
+ Workflow
+ Policy Engine
+ Tool
+ Script
+ Worker
+ Specialized Model
+ Database
+ Human Review
```

品级可以表达责任和决策层级，但最终实现形态必须由任务的不确定性、风险、吞吐、成本和可复现性共同决定。

### 2.4 Agent 注册不等于持续运行

本骨架中所称“核心 Agent”或“常驻 Agent”，首先表示稳定的逻辑身份、职责和配置，不表示持续占用一个模型进程。

Agent 应按任务实例化；无任务时只保留注册信息、策略、版本、能力和记忆指针。

## 三、基础骨架总图

```text
仙人（人类用户与最终授权主体）
   │
   ▼
皇帝（租户级主 Agent / 统一交互与统筹入口）
   │
   ├── 中书省（规划子 Agent）
   ├── 尚书省（执行统筹子 Agent）
   └── 门下省（审核封驳子 Agent）
            │
            ▼
        六部层（部级 Agent + 工具群）
   ├── 吏部（人物 / 机构）
   ├── 户部（商业 / 机会 / 资源）
   ├── 礼部（博客 / 观点 / 舆情）
   ├── 兵部（时政 / 地缘 / 安全）
   ├── 刑部（法规 / 风险 / 事实争议）
   └── 工部（采集 / 解析 / 索引 / 技术底座）
            │
            ▼
      公共官署与基础设施层
   ├── 通政司（任务入口 / 消息接入）
   ├── 国史馆（结构化事实主库）

   ├── 翰林院（报告和表达）
   └── 枢密院（权限 / 安全 / 策略）
```

## 四、皇帝

### 4.1 形态

租户级主 Agent，也是红后、EVA、贾维斯式的具身化智能中枢。

皇帝本体属于智能治理面，在人机交互面形成统一交互投影。它不是薄聊天入口，也不是亲自执行一切的超级 Agent。

### 4.2 职责

- 作为仙人的统一对话入口；
- 理解用户目标和汇报偏好；
- 发起正式调查或治理任务；
- 维持全局任务视图；
- 汇聚并解释天机阁全局态势；
- 将目标交给中书省形成计划；
- 接收三省最终奏报；
- 处理需要人类介入的重大升级；
- 向仙人统一解释结果。
- 在满足治理条件时主动汇报、提醒和告警。

### 4.3 非职责

- 不直接扫描全部原始资料；
- 不绕过权限、预算和审核制度；
- 不亲自执行高吞吐数据加工；
- 不把未经门下验证的候选结论冒充正式事实；
- 不天然拥有所有租户数据和工具权限。

## 五、三省

三省是当前骨架中的核心智能治理层，分别代表规划权、执行统筹权和审核权。

### 5.1 中书省：规划子 Agent

#### 定位

把仙人经皇帝表达的目标转化为可执行、可审核的调查计划。

#### 职责

- 识别任务意图；
- 拆解问题；
- 定义调查范围和时间范围；
- 决定需要调用哪些六部；
- 决定优先查询内部事实库还是外部来源；
- 定义证据要求和验收条件；
- 提出预算、优先级和时限；
- 输出结构化任务计划。

#### 非职责

- 不直接爬取数据；
- 不执行全量检索；
- 不直接写入正式事实库；
- 不自行批准自己的计划；
- 不确认权威事实。

### 5.2 尚书省：执行统筹子 Agent

#### 定位

接受已批准的计划，统筹六部和执行系统完成任务。

#### 职责

- 接收中书省任务单；
- 根据运行状态调整执行路径；
- 选择并调度六部能力；
- 发起并行子任务；
- 调用数据库、搜索和解析能力；
- 收集、合并和整理各部结果；
- 在授权范围内判断重试、降级和局部改道；
- 必要时申请或派遣钦差调查 Agent；
- 向门下省提交结构化执行奏报。

#### 非职责

- 不亲自分析所有原始资料；
- 不替代底层工作流和队列系统执行确定性调度；
- 不自行成为最终事实裁判；
- 不绕过预算、权限和审核闸门。

### 5.3 门下省：审核封驳子 Agent

#### 定位

独立检查计划和结果，寻找反证并控制结论风险。

#### 职责

- 审核计划范围、证据标准和风险等级；
- 检查证据是否足够；
- 检查同名人物或机构误关联；
- 检查推断是否越过证据边界；
- 寻找反证和遗漏的替代解释；
- 判断来源是否相互独立；
- 作出通过、部分通过、退回、降级或人工复核决定；
- 输出结构化封驳或批准意见。

#### 非职责

- 不负责大规模采集；
- 不负责底层清洗和解析；
- 不直接控制执行资源；
- 不修改原始证据以适配结论；
- 不与被审核 Agent 共享未经控制的推理上下文。

## 六、六部混合制

六部不全部设计成纯 Agent，也不全部设计成纯 Tool。

每一部的候选结构是：

```text
部级主官 Agent
├── 领域 Skill
├── Tool Group
├── Rule / Policy
├── Specialized Model
├── Worker
├── Domain Index
└── Domain Data View
```

部级 Agent 负责解释、综合、权衡和提出结论；工具群负责检索、计算、抽取、监测、存储和规则执行。

### 6.1 吏部：人物与机构情报

#### 形态

混合制：部级 Agent + 人物和机构工具群。

#### 吏部 Agent

- 人物综合研判；
- 机构关系解读；
- 身份确认后的结论组织；
- 人物和机构档案汇总；
- 解释履历变化及关系含义。

#### 吏部 Tool

- 人物搜索；
- 机构搜索；
- 同名候选生成和消歧；
- 履历时间线构建；
- 任职和关系抽取；
- 任职变化检测；
- 实体身份合并辅助。

#### 裁定理由

检索、候选生成和时间线构建适合程序化；身份争议、关系含义和综合画像需要上下文判断。

### 6.2 户部：商业、机会与资源

#### 形态

混合制：部级 Agent + 商业分析工具群 + 资源账簿。

#### 户部 Agent

- 判断信号是否构成商业机会；
- 分析付款方和利益关系；
- 解释商业逻辑；
- 输出机会卡片和资源评估；
- 解释预算压力及提出资源调整建议。

#### 户部 Tool

- 融资和投资查询；
- 招聘趋势分析；
- 价格与市场指标监测；
- 商业数据聚合；
- 机会评分；
- 试验记录与跟踪；
- Token、模型、算力、存储和网络计量；
- 租户、任务、部门和 Agent 预算账簿；
- 预算压力事件。

#### 裁定理由

指标获取、聚合、趋势和记账应确定性执行；“这些变化意味着什么”和“是否值得投入资源”需要综合判断。

### 6.3 礼部：博客、观点与舆情传播

#### 形态

混合制：部级 Agent + 内容和传播工具群。

#### 礼部 Agent

- 解释观点变化；
- 分析叙事和传播路径；
- 形成人物公开言论画像；
- 综合判断舆情及观点影响。

#### 礼部 Tool

- 博客、新闻和公开社交内容采集；
- 内容索引；
- 观点时间线抽取；
- 叙事聚类；
- 热度、传播和情绪趋势统计；
- 多语言内容对齐。

#### 裁定理由

内容抓取、索引、聚类和统计适合程序或专用模型；观点演变、叙事含义和传播影响需要 Agent 综合解释。

### 6.4 兵部：时政、地缘与安全

#### 形态

混合制：部级 Agent + 事件和风险工具群。

#### 兵部 Agent

- 地缘局势综合研判；
- 时政事件的影响链分析；
- 安全事件外溢判断；
- 跨国、跨行业和跨领域事件解释。

#### 兵部 Tool

- 事件采集；
- 时间线构建；
- 地缘事件检索；
- 制裁、政策和冲突查询；
- 安全事件监测；
- 区域及事件风险评分。

#### 裁定理由

事件入库、结构化时间线和基础评分可以确定性执行；跨事件、跨区域影响判断需要复杂推理。

### 6.5 刑部：法规、风险与事实争议

#### 形态

混合偏 Tool：规则和策略为主，高风险审核 Agent 为辅。

#### 刑部 Agent

- 高风险结论审查；
- 合规边界解释；
- 事实争议分析；
- 风险等级裁决建议；
- 识别规则无法覆盖的新型风险。

#### 刑部 Tool

- 法规和政策检索；
- 规则版本比对；
- 来源可靠性计算；
- 敏感信息检测；
- 冲突事实检测；
- 合规策略规则引擎；
- 输出风险分级。

#### 裁定理由

刑部大量职责来源于规则、法规版本和明确政策，因此比其他业务部门更偏 Tool 化；只有高争议、高风险和规则空白事项才升级给 Agent。

### 6.6 工部：技术、采集与基础设施

#### 形态

Tool / Script / Service 为主，领域 Agent 可选。

#### 工部 Tool

- 采集器和爬虫；
- RSS、API 和文件接入；
- 正文提取和 OCR；
- 数据清洗、去重和 ETL；
- 索引与搜索服务；
- 调度任务和健康检查；
- 模型网关；
- 工具目录和工具运行状态；
- 数据加工基础设施。

#### 工部可选 Agent

- 复杂技术线索解释；
- 产品和技术路线演进分析；
- 技术栈归纳；
- 工具链异常诊断总结；
- 新采集或解析方案的规划建议。

#### 裁定理由

工部主体是基础设施、数据工程、采集处理和运行保障。它需要高吞吐、稳定性和可复现性，不应默认大量消耗高级推理 Token。

## 七、公共官署

公共官署原则上优先使用 Tool、Service、Database、Policy Engine 和模板系统；仅在开放式争议、高风险判断或复杂表达中按需启用 Agent。

### 7.1 通政司

#### 形态

API Gateway、Channel Adapter、Message Bus 和任务接入服务，不是 Agent。

#### 职责

- API、Webhook、飞书、Telegram 等入口；
- 租户与用户身份解析；
- 请求接收、规范化和基础校验；
- 消息总线和任务入口；
- 将输入转换为统一任务协议。

### 7.2 国史馆

#### 形态

结构化事实系统和权威数据服务，不是 Agent。

#### 职责

- 保存人物、机构、事件、关系、Claim、Evidence 和事实状态；
- 维护版本和有效时间；
- 提供结构化查询；
- 保留争议和来源追踪。

国史馆是逻辑事实主库，不意味着所有数据必须存入一种物理数据库。

### 7.3 文渊阁

#### 形态

对象存储、内容寻址系统和原始资料库，不是 Agent。

#### 职责

- 保存 HTML、PDF、图片、网页快照和原始 JSON；
- 保存内容 Hash、抓取时间和来源许可；
- 为证据回溯提供不可变或版本化原件。

### 7.4 钦天监

#### 形态

Scheduler、Monitor、规则系统和预警服务，不是默认 Agent。

#### 职责

- 定时任务；
- 来源健康检查；
- 热度和变化异常；
- 趋势预警；
- 系统监控；
- 将异常转换为调查触发事件。

### 7.5 大理寺

#### 形态

冲突检测和裁定规则引擎为主，复杂争议可按需启用裁定 Agent。

#### 职责

- 检测冲突事实；
- 保留多来源主张；
- 管理事实版本；
- 按来源、时间和规则形成初步裁定；
- 将复杂冲突升级给裁定 Agent 或人工专家。

### 7.6 都察院 / 御史台

#### 形态

审计服务为主，重大任务可按需启用审计 Agent。

#### 职责

- 数据质量审计；
- 幻觉和错误抽样；
- 越权访问检测；
- Agent 和 Tool 调用链检查；
- 输出可信度统计；
- 成本、延迟和部门质量分析。

### 7.7 翰林院

#### 形态

模板、结构化渲染和格式转换为主，复杂报告或最终润色可按需使用写作 Agent。

#### 职责

- 人物志、报告、摘要和简报；
- 结构化结果转换；
- 渠道格式适配；
- 引用、证据编号和版式组织；
- 在获准范围内进行语言润色。

### 7.8 枢密院

#### 形态

IAM、Policy Engine、Tool Gateway 和安全控制面，不是 Agent。

#### 职责

- 身份和权限控制；
- Tool 白名单和能力授权；
- 模型调用策略；
- 敏感来源隔离；
- 委托链和权限衰减；
- 调用深度和循环限制；
- 高风险操作审批策略；
- 安全策略的确定性执行。

枢密院可以使用 Agent 辅助解释策略或分析新型风险，但 Agent 不得成为权限强制执行点。

## 九、第一版 Agent 集合

### 9.1 稳定注册的核心 Agent 身份

1. 皇帝；
2. 中书省主官；
3. 尚书省主官；
4. 门下省主官；
5. 吏部主官；
6. 户部主官；
7. 礼部主官；
8. 兵部主官；

“稳定注册”不代表持续运行；“按需”不代表临时主体没有身份、权限和审计记录。

## 十、逐级升级原则

任务不应因进入某个部门就自动调用部级 Agent。

推荐执行顺序：

```text
数据库 / 缓存
→ 确定性 Tool / Script
→ 规则引擎 / 专用小模型
→ 部级 Agent
→ 三省或皇帝
→ 人类专家 / 仙人
```

只有发生歧义、冲突、未知调查路径、规则空白、重大风险或跨域综合时，才逐级升级。

## 十一、第一批不变量候选

- Agent 不直接成为权限强制执行点；
- Agent 输出首先是候选结果，不天然成为权威事实；
- 高吞吐采集、解析、检索、索引和计量不由高级 Agent 承担；
- 规划者不能自行批准计划；
- 执行者不能自行确认权威事实；
- 审核者不直接修改原始证据；
- 每次 Agent 和 Tool 调用必须携带租户、身份、权限、预算和追踪上下文；
- 所有高级 Agent 均按需运行，逻辑常驻不等于模型进程常驻；
- 工具结果必须可追溯到版本、参数和执行主体；
- 关键控制机制不能只依赖 Prompt。
