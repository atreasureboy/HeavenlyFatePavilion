# 情报语义与核心对象深化计划

状态：Accepted

生效日期：2026-07-24

## 一、定位

本文是 `Skeleton v1.0` 之后第一个专题深化入口。

它不直接给出所有对象的最终定义，而是规定情报语义应按什么依赖顺序细化、怎样避免过早技术化，以及达到什么标准才可以进入数据和协议设计。

## 二、为什么是第一专题

天机阁的核心难题不是“存多少数据”，而是：

```text
一份资料说了什么
→ 哪个片段可以作为证据
→ 谁提出了什么主张
→ 天机阁在何种范围内接受什么事实
→ 哪些现实对象、关系和变化可以被确认
→ 这些事实意味着什么
→ 未来可能怎样发展
→ 哪些风险需要告警
→ 产品如何引用并承担纠正义务
```

这条链是数据架构、Agent 协作、审核、审计、搜索和产品的共同依赖。

## 三、三条设计纪律

### 3.1 先语义，后存储

逻辑对象不预设一对象一表，也不预设关系库、图库、文档库或向量库。

### 3.2 先权威，后流程

先回答谁能够创建、接受、争议、撤回和替代对象，再回答工作流如何自动化。

### 3.3 先失败，后顺利

每个对象必须同时用正常形成和以下异常进行验证：

- 来源后来修改；
- 抽取器版本变化；
- 同名实体误合并；
- 多个来源相互冲突；
- 新证据推翻旧事实；
- 预测到期但无法验证；
- 产品已经外发后上游被撤回；
- 租户私有判断不得污染公共知识。

## 四、十步深化树

| 步骤 | 核心问题 | 主要产出 |
|---|---|---|
| S1 | 有哪些语义层，术语是否唯一 | 统一语言、对象分类 |
| S2 | 原始世界怎样被保真记录 | Source、Document、Snapshot、Evidence |
| S3 | 一句话怎样从主张成为事实 | Claim、Dispute、Fact、Decision |
| S4 | “它是谁”怎样成立 | Entity、Identity、Alias、Resolution |
| S5 | 世界怎样发生变化 | Relationship、Event、State、Diff、Change |
| S6 | 系统怎样从事实推到未来 | Signal、Assessment、Forecast、Scenario、Risk |
| S7 | 结论怎样交付并产生影响 | Product、Alert、Feedback、Action、Effect |
| S8 | 同一对象怎样跨时间和作用域存在 | 双时态、版本、租户覆盖、联合空间 |
| S9 | 怎样保证可追溯、可撤回、可纠正 | 权威、血缘、生命周期、不变量 |
| S10 | 是否足以约束后续架构 | 场景矩阵、语义评审、基线 |

## 五、每种对象的统一说明模板

后续每个正式对象至少回答：

1. 它表示现实、陈述、判断、控制还是交付；
2. 它为什么需要独立身份；
3. 谁创建、谁接受、谁可以争议或撤回；
4. 它属于公共、租户、联合还是任务作用域；
5. 它有哪些有效时间、系统时间和认识时间；
6. 它怎样版本化；
7. 它依赖哪些输入；
8. 哪些下游对象依赖它；
9. 发生冲突、迟到、撤回和重解释时怎样处理；
10. 它明确不是什么。

## 六、专题出口

完成本专题后，才能稳定进入：

```text
对象语义基线
├── 契约与事件协议
├── 数据与存储架构
├── 实体解析、关联和 Diff 流水线
├── 门下审核与大理寺事实裁定
├── 多租户知识覆盖
├── 情报产品引用与更正
└── 质量评测和审计
```
