# 天机阁架构总纲

状态：初始立项  
性质：纯架构设计  
实现要求：无  
主要用途：系统化研究及架构能力展示

## 一、设计目标

天机阁不是单个情报 Agent，也不是简单的信息聚合或检索产品。它是一套多租户、证据驱动、持续运行、全程可审计的企业级智能情报平台架构。

本项目通过一个足够复杂且边界明确的业务领域，系统性展示以下架构能力：

1. 从业务目标和质量属性推导系统边界；
2. 对超大型系统进行领域分解和职责划分；
3. 建立跨服务、跨存储和跨执行主体的统一语义；
4. 处理分布式环境中的并发、失败、一致性和恢复；
5. 设计可强制执行的权限、安全和治理机制；
6. 对性能、容量、成本和准确性进行定量权衡；
7. 使用架构决策记录解释重要选择及被放弃的方案；
8. 设计系统从早期形态向终局形态的演进路径。

## 二、业务边界

系统允许处理：

- 公开网页和开放数据；
- 官方公告及公开记录；
- 合法授权的数据接口；
- 用户主动提交的资料；
- 租户拥有合法处理权限的内部数据。

系统不以泄露数据、隐私检索、秘密监控或个人敏感信息聚合作为产品能力。

公开可访问不等于允许无限制采集、保存或商业利用。来源许可、版权、访问策略、删除请求、数据保留期和数据主体纠错权均属于架构的一部分。

## 三、系统分层

```text
天机阁情报产品
查询 / 监测 / 档案 / 时间线 / 简报 / 预警 / 专题研判
                            │
                            ▼
天机阁领域与治理系统
三省六部 / 实体 / 事件 / 事实 / 证据 / 情报产品
                            │
                            ▼
AgentOS 运行基座
Run / Task / Worker / Tool / Memory / Scheduler / Event Log
                            │
                            ▼
企业基础设施
数据库 / 搜索 / 图谱 / 对象存储 / 队列 / 模型 / 计算节点
```

AgentOS 解决 Agent 如何安全、并发、可控且可审计地运行。

天机阁解决合法信息如何被收集、关联、验证并转化为情报产品。

## 四、核心业务主链

```text
Source
  → Document
  → Snapshot
  → Evidence
  → Claim
  → Verification
  → Fact / Disputed Claim
  → Entity / Event / Relationship
  → Signal
  → Assessment
  → Intelligence Product
```

这条主链是各专题设计必须共同遵守的语义骨架。任何服务、Agent、数据存储和异步任务都不得私自改变这些概念的含义。

## 五、核心质量属性

按当前优先级排列：

1. 可追溯性；
2. 事实可信度；
3. 租户隔离与安全；
4. 数据和任务语义的一致性；
5. 可审计性；
6. 故障恢复能力；
7. 可扩展性；
8. 成本可控性；
9. 性能与时效性；
10. 架构可演进性。

具体设计中出现冲突时，应记录取舍，不能默认所有质量属性可以同时最大化。

## 六、三省治理原则

中书省负责形成调查计划、证据要求、成本边界和验收条件，但不能确认权威事实。

尚书省负责任务分发、并行执行、资源调度、超时重试和结果聚合，可以提交候选事实，但不能自行将候选事实升级为权威事实。

门下省负责检查证据、寻找反证、识别身份误关联、判断结论是否超出材料，并作出通过、部分通过、退回、降级或转人工复核的决定。

三省代表权力和职责分离，不要求每个任务机械地依次调用三个大模型。

## 七、设计方法

整个架构采用四种相互校验的组织方式：

### 主题卷

分别描述领域、数据、运行、安全、质量、成本和演进。

### 标准场景

用一组固定的复杂场景贯穿全部专题，验证跨层设计能否闭合。

### 架构决策记录

记录背景、约束、候选方案、最终决定、代价和重新评估条件。

### 架构不变量

明确无论部署方式、技术选型和系统规模如何变化，都必须保持成立的约束。

## 八、首批标准场景

1. 调查存在大量同名候选人的企业高管；
2. 持续监测一家企业并发现重大经营变化；
3. 多个高可信来源对同一任职事实产生冲突；
4. 恶意网页试图通过提示词注入操纵调查 Agent；
5. 突发事件引起采集、检索和研判流量暴涨；
6. 租户要求删除私有资料及其全部派生结果；
7. 模型供应商故障、降级或价格大幅变化；
8. Agent 形成证据不足但可能造成重大影响的判断。

## 九、非目标

- 不以编写可运行代码作为项目完成标准；
- 不为展示技术数量而堆叠中间件；
- 不把所有业务过程强行转换成 Agent；
- 不使用人格化命名替代正式的职责、协议和权限设计；
- 不假定模型输出天然可信；
- 不用单一向量数据库代替事实、证据和事务系统；
- 不追求一张图覆盖全部架构细节。

## 十、完成标准

本架构没有以字数定义的完成标准。每个重要能力至少应具备：

- 明确的业务目标和边界；
- 领域概念与不变量；
- 组件职责和所有权；
- 输入、输出及协议；
- 正常流程和异常流程；
- 数据一致性及并发语义；
- 权限与威胁分析；
- 可观测性和审计要求；
- 容量与成本假设；
- 方案权衡和演进条件。

当各专题能够通过标准场景相互验证，并且关键决策不存在未解释的矛盾时，架构才可视为阶段性闭合。
