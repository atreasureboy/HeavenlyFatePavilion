# 天机阁主体生态与分域主权骨架

状态：Accepted

生效日期：2026-07-24

## 一、目的

系统上下文回答“边界内外有什么”，本文进一步回答：

- 谁使用、运营、供应、约束、影响或被天机阁影响；
- 每类主体对什么拥有原生权威；
- 哪些权力只能被委托，不能由 Agent 自行产生；
- 哪些外部状态永远不由天机阁拥有；
- 当权威来源冲突时，骨架应把问题送到哪里。

本文只建立宏观主体与权威拓扑，不定义角色权限字段、法规优先级表和审批流程。

## 二、生态主体全表

### 2.1 需求与受益主体

```text
租户所有者
├── 为仙门设定目标、预算、制度和责任边界
├── 仙人 / 业务决策者
├── 分析师 / 调查者
├── 普通查询者
├── 产品订阅者 / 告警接收者
└── 下游业务责任人
```

发起问题、消费情报、批准资源、承担业务决定可能是不同的人。不能把所有人都压缩成一个“用户”角色。

### 2.2 平台治理与运营主体

```text
平台所有者 / 宪制治理者
平台运营者
安全、隐私、合规与风险职能
平台审计者
基础设施运营者
人类应急控制者
```

平台运营者拥有运行职责，不自动拥有租户数据的业务使用权。平台所有者可以制定平台准入规则，但不能把外部法律、数据权利或租户合法所有权视为不存在。

### 2.3 知识与专业主体

```text
领域专家
事实裁定者
质量审核者
外部研究机构
数据提供者与来源维护者
事实纠正提出者
```

他们可以贡献证据、领域解释、裁定和反馈。专业意见本身仍需标明主体、范围、版本和利益关系。

### 2.4 权利人与被研究主体

```text
数据所有者 / 数据控制者
内容与知识产权权利人
个人数据主体
被研究的人物、企业、组织和项目
事件当事方
受到报告、告警或外部行动影响的第三方
```

“被研究对象”不是系统组件，也不一定是用户，但其数据权利、更正请求、合法利益和被影响关系必须在生态骨架中有位置。

天机阁记录关于现实世界的主张，不因记录行为取得对被研究对象的控制权。

### 2.5 公共与制度约束主体

```text
立法、司法、行政与监管机构
行业自律与标准组织
数据保护与知识产权机构
司法裁判、许可和制裁发布者
公共利益代表与独立监督者
```

这些主体可能改变合法性、保留、地域、来源准入、产品分发和外部行动边界。天机阁消费并执行其适用约束，不拥有这些制度的制定权。

### 2.6 能力与供应链主体

```text
模型提供者
Tool / Skill / 插件开发者
搜索、OCR、翻译和数据服务商
云、网络、存储和计算供应商
身份与信任服务提供者
外部 Agent Runtime / AgentOS
开源社区与依赖维护者
能力市场和集成商
```

供应商拥有其服务内部状态和合同能力；天机阁拥有是否准入、如何调用、如何验证、如何隔离以及如何替换的治理责任。

### 2.7 外部系统与同行生态

```text
租户 CRM / ERP / 工单 / 知识系统
通知、支付、交易与控制系统
数据交换平台
其他情报与知识系统
联合调查空间和同行联盟
外部归档、审计与取证系统
人类协作平台
```

这些系统既可能是数据来源、产品消费者，也可能拥有外部行动的最终状态。天机阁不能把对方系统的成功响应直接等同于现实业务结果。

### 2.8 非合作与对抗主体

```text
恶意内容发布者
提示词注入与数据投毒者
凭证窃取者
内部滥用者
虚假身份与协同行为网络
不可靠、被攻陷或停止服务的供应商
```

对抗主体不需要拥有合法系统账户，也能通过公开内容、来源、供应链或下游传播影响天机阁。它们属于生态模型，不能只留到安全细节阶段才出现。

## 三、系统内部主体

天机阁内部主体分为四类：

| 类别 | 例子 | 权力来源 |
|---|---|---|
| 稳定逻辑身份 | 皇帝、常设官职、平台服务身份 | 平台与租户配置 |
| 临时执行主体 | Agent Instance、Worker、Run、Task 执行者 | 有期限的委托与能力令牌 |
| 确定性强制主体 | 策略、预算、数据、审计、生命周期执行点 | 版本化平台政策 |
| 治理与记录主体 | 三省、六部主官、大理寺、都察院、权威存储 | 明确职责、决定权或记录权 |

内部主体只能拥有派生权力。模型能力更强、上下文更多或角色名称更高，不会自动扩大授权。

## 四、分域主权模型

天机阁不采用“一个主体拥有一切”的单中心主权，而采用分域权威：

| 主权域 | 原生权威主体 | 天机阁的角色 |
|---|---|---|
| 人类目标与最终责任 | 有权仙人、租户治理者、外部责任人 | 解释、规划、建议、请求决定 |
| 平台宪制与运行 | 平台治理者和运营者 | 执行平台政策并提供控制证据 |
| 租户组织与资源 | 租户所有者及获授权管理员 | 维护 Court Profile、预算与逻辑朝廷 |
| 个人与角色权限 | 身份权威、租户治理和适用制度 | 解析身份、验证委托、限制动作 |
| 数据使用与处置 | 数据权利人、租户、来源许可与适用制度 | 在许可范围内处理并履行处置义务 |
| 外部来源内容 | 来源发布者拥有原始发布状态 | 快照、证据化、验证，不替来源改写历史 |
| 事实与知识状态 | 无主体拥有“现实真相”；验证制度拥有系统内接受权 | 保存主张、证据、争议和可纠正的 Fact |
| 情报研判 | 有权研判与审核主体 | 形成带范围、不确定性和时限的 Assessment |
| 产品与表达 | 产品所有者、发布决定者和受众策略 | 版本化生成、审核、分发和更正 |
| 外部业务状态 | 外部业务/行动系统及其责任主体 | 提议或受控调用，验证回执与现实结果 |
| 法律与公共约束 | 适用司法辖区、监管和权利制度 | 识别、执行、记录并升级冲突 |
| 能力版本 | 平台治理与获授权发布主体 | 实验、评测、灰度、发布和回滚 |

### 4.1 事实域的特殊性

事实不能被设计成“谁权力最大谁就能改写”：

```text
来源拥有其发布记录
证据拥有不可变引用
Claim 保留提出者
验证制度决定系统内接受状态
争议主体可以提出挑战
新证据可以触发纠正
```

所以，事实的“权威”是可追溯、可争议、可纠正的认识论权威，不是政治或组织所有权。

### 4.2 皇帝的权力性质

皇帝是租户级智能中枢和治理代表，但不拥有原生主权：

```text
皇帝有效权力
= 平台允许能力
∩ 租户 Court Profile
∩ 当前仙人权限
∩ Mission 委托
∩ 数据与来源许可
∩ 风险、预算和时间条件
```

皇帝可以统筹和解释，不能替人类创造授权、替来源创造事实、替外部系统创造业务结果、替监管者改变规则。

## 五、生态关系类型

主体与天机阁之间至少存在九类不同关系：

1. `Govern`：制定适用制度或组织规则；
2. `Authorize`：授予有限能力、数据或行动权限；
3. `Request`：提出目标、查询或服务请求；
4. `Supply`：提供数据、模型、Tool、算力或专业知识；
5. `Observe`：成为合法调查、监测或评测对象；
6. `Review`：审核事实、研判、产品或系统行为；
7. `Consume`：接收情报、告警、API 或决定支持；
8. `Act`：拥有并改变外部业务状态；
9. `Challenge`：纠正、申诉、撤回、审计或对抗。

同一主体可以同时拥有多种关系，但关系不能自动互相推出。例如：

- 数据供应者不自动拥有租户产品读取权；
- 产品消费者不自动拥有底层证据下载权；
- 平台运营者不自动拥有租户业务决定权；
- 被研究主体有纠正权，不自动拥有删除合法公共事实的绝对权；
- Tool 供应者不拥有其调用结果的事实接受权。

## 六、权威冲突的骨架路由

当前不预设所有司法辖区和组织的完整优先级，但冲突必须按域显式化：

```text
发现 Authority Conflict
→ 标记冲突涉及的主权域、主体、作用域和时间
→ 停止不可逆或高影响路径
→ 平台控制面执行明确的硬约束
→ 智能治理面组织证据和候选解释
→ 枢密院识别权限与政策冲突
→ 刑部提供法规与合规领域分析
→ 大理寺处理事实主张冲突
→ 都察院保全审计并检查程序
→ 交有权人类或外部权威作最终决定
```

不同冲突不能全部交给一个“超级审核 Agent”。事实冲突、法律冲突、组织授权冲突和外部业务责任冲突拥有不同裁定者。

## 七、系统边界与责任边界

### 7.1 天机阁拥有

- 自身对象、契约、状态、运行和审计语义；
- 对外部输入的准入、快照、验证和使用责任；
- 对 Agent、模型、Tool 和供应链的调用治理；
- 对内部产品、告警和建议的证据与表达责任；
- 在授权外部行动中的请求、审批、调用、验证和补偿编排记录；
- 自身能力版本与演进过程。

### 7.2 天机阁不拥有

- 现实世界主体本身；
- 外部来源的原始发布权；
- 法律、监管、许可和权利制度的制定权；
- 租户之外的人类最终责任；
- 外部供应商的内部实现和可用性；
- 外部业务系统的最终权威状态；
- “现实真相”的不可争议垄断权；
- 未经授权的数据、工具、资源和行为能力。

## 八、骨架不变量

| 编号 | 不变量 |
|---|---|
| INV-0009 | 所有 Agent 和内部服务的权力都是派生、限域、限时且可撤销的。 |
| INV-0010 | 平台运营责任不自动产生租户业务数据使用权。 |
| INV-0011 | 数据供应、事实接受、产品消费和外部行动是四种不同权力。 |
| INV-0012 | 被研究主体与受影响第三方必须在生态模型中可表示。 |
| INV-0013 | 外部业务状态由对应外部系统与责任主体拥有，调用成功不等于现实结果成立。 |
| INV-0014 | 事实接受权来自可审计验证制度，不能由组织权力或模型自信直接替代。 |
| INV-0015 | 权威冲突必须按主权域分流，不得交给单一 Agent 自我裁定。 |

## 九、仍然开放

- 法律、数据权利、平台宪制、租户制度和用户指令的冲突优先级；
- 被研究主体的纠正、异议、删除与公共利益之间的边界；
- 外部行动能力是否属于天机阁终局必要能力；
- 同行天机阁或异构情报系统之间的联邦信任；
- 能力市场、第三方 Skill 和未来 Agent 的责任分配；
- 无法确定适用辖区时的默认治理路径。

这些问题保留为后续骨架扫描和专题裁定，不能通过“皇帝拥有最高权力”提前抹平。
