# 天机阁系统上下文与边界

状态：Accepted

生效日期：2026-07-24

## 一、上下文结论

天机阁是一个共享平台承载的多租户 Agent 化情报与知识治理系统。

其上下文采用四层主体模型：

```text
天界平台
└── 仙门租户
    └── 逻辑朝廷
        ├── 皇帝稳定身份与 Court Profile
        ├── 三省六部及官署能力配置
        └── 按任务创建的 Agent / Run / Task 实例
```

平台能力可以共享，租户朝廷在逻辑上独立；稳定身份、配置和记录可以长期存在，执行 Agent 不要求永久常驻。

## 二、系统上下文全景

```text
人类与组织
├── 平台运营者
├── 仙门租户所有者
├── 仙人 / 租户成员
├── 外部协作者
└── 人类专家与审批者
          │
          ▼
┌──────────────────────── 天机阁系统边界 ────────────────────────┐
│                                                                │
│  体验与交付：皇帝交互投影、渠道、情报产品                      │
│  情报生产：掌数、联结、察变、推势、卜算、警险、六部能力        │
│  治理与执行：皇帝本体、三省、运行时、Agent、Tool、Worker       │
│  平台与知识：数据底座、租户控制、策略、目录、预算与版本        │
│  演进与适应：观察、实验、评测、发布与回滚                      │
│                                                                │
└───────────┬───────────────┬──────────────┬──────────────┬─────┘
            │               │              │              │
            ▼               ▼              ▼              ▼
      外部数据世界      外部智能能力     外部业务系统     外部交互渠道
```

## 三、人类与组织主体

### 3.1 平台运营者

负责共享天界平台的能力供应、平台级配置、基础设施和租户生命周期。

平台运营者不是任一仙门的仙人，也不因运营平台而自动取得租户私有情报的业务使用权。

### 3.2 仙门租户

仙门是多租户边界中的组织主体，拥有：

- 独立租户标识；
- 成员与角色；
- Court Profile；
- 私有数据覆盖层；
- 调查目标和历史；
- 策略、预算和模型偏好；
- 皇帝稳定身份；
- 情报产品与审计记录。

仙门是逻辑隔离单元，不代表必须复制一整套物理平台。

### 3.3 仙人

仙人是与皇帝建立关系的人类主体。一个仙门可以有多位仙人，不同仙人可以具有不同角色、关注范围和决定权。

仙人可以提出目标、问题、纠正和决定；系统不能把租户所有者、普通成员、外部协作者和人类专家默认视为同等权限主体。

### 3.4 外部协作者与人类专家

外部协作者可以在受控空间中提供资料、反馈或共同调查。人类专家可以参与事实裁定、领域复核、风险判断和演进评测。

二者属于天机阁外部人类主体，其输入、决定和责任记录进入系统，但其个人或组织本身不属于天机阁内部组件。

### 3.5 权利人、被研究主体与受影响第三方

个人数据主体、数据与内容权利人、被研究的人物/企业/组织、事件当事方和受到产品或行动影响的第三方，也是系统生态主体。

他们不因不是用户而失去架构位置。其来源权利、更正、异议、合法处置请求和受影响关系必须可表示；天机阁记录关于现实世界的主张，不取得对现实主体本身的控制权。

### 3.6 公共与制度约束主体

立法、司法、行政、监管、标准和独立监督主体位于天机阁边界外。它们可能改变数据使用、地域、保留、来源、产品和外部行动边界。

天机阁负责识别和执行适用约束，不拥有这些制度的制定权。

## 四、租户朝廷与皇帝模型

### 4.1 共享平台与逻辑朝廷

```text
共享天界平台
├── 公共平台能力
├── 合法共享的公共资料与事实
├── 通用模型、Tool、Skill 与运行设施
│
├── 仙门 A
│   ├── Court Profile A
│   ├── 皇帝身份 A
│   ├── 私有覆盖层 A
│   └── Run / Agent 实例 A
│
└── 仙门 B
    ├── Court Profile B
    ├── 皇帝身份 B
    ├── 私有覆盖层 B
    └── Run / Agent 实例 B
```

共享的是平台能力和明确允许共享的公共资料，不是租户意图、私有资料、派生研判、凭证或对话历史。

### 4.2 皇帝稳定身份

每个仙门默认拥有一个逻辑皇帝身份。该身份提供：

- 对仙门保持一致的系统人格；
- 长期关系与偏好连续性；
- 朝廷治理入口；
- 全局任务和情报态势视图；
- 主动汇报与解释责任；
- 稳定审计主体。

皇帝稳定身份不等于一个永久占用模型和算力的进程。

### 4.3 皇帝运行实例

皇帝可以按会话、事件或任务创建运行实例。实例加载：

```text
平台基线
+ Court Profile
+ 皇帝稳定身份
+ 当前仙人身份与角色
+ 当前会话上下文
+ 当前 Mission / Run 上下文
+ 权限、预算、风险和追踪上下文
```

实例结束后，运行时上下文按生命周期处置；应长期保留的事实、决定、偏好和审计记录写入各自的权威存储，而不是依赖模型上下文永久存在。

### 4.4 Court Profile

Court Profile 是租户逻辑朝廷的版本化期望状态，至少包含：

- 租户身份、成员和组织关系；
- 皇帝人格与交互偏好；
- 启用的三省六部和官署能力；
- 允许的数据源、Tool、Skill 和模型；
- 领域关注与长期监测目标；
- 证据和质量标准；
- 风险、审批和升级策略；
- 预算、配额和资源政策；
- 输出产品、语言、渠道和频率；
- 私有记忆与数据范围引用；
- 配置版本及生效条件。

Court Profile 属于平台控制面的长期期望状态；它不是某次 Run 的即时状态。

## 五、天机阁系统边界内

以下逻辑责任属于天机阁：

- 租户、皇帝和朝廷的逻辑模型；
- 人机交互与情报产品；
- 数据认知与情报研判；
- 三省治理和六部领域能力；
- Agent、Tool、Skill、模型调用和任务运行；
- 原始资料、证据、事实、关系、变化、研判和产品记录；
- 平台控制、预算、版本和策略；
- 能力观察、评测和演进闭环；
- 对外部系统的适配、调用记录、结果验证和失败处理；
- 天机阁自身的审计、可观测和责任追踪。

## 六、天机阁系统边界外

下列主体或能力由天机阁使用、协作或影响，但不由天机阁拥有其内部实现：

### 6.1 外部数据世界

- 公开网站、新闻、博客和社交平台；
- 法规、工商、招聘、市场和学术数据源；
- RSS、开放 API 和商业数据服务；
- 租户上传资料；
- 租户授权的企业内部数据源；
- 传感器、日志和事件流。

天机阁拥有来源接入、快照、解析、证据化和追踪责任，不拥有外部来源自身的真实性或持续可用性。

### 6.2 外部智能与技术供应商

- 外部模型提供者；
- 搜索、OCR、翻译和专用分析服务；
- 身份提供者；
- 云、网络和基础设施供应商；
- AgentOS 或其他未来运行平台。

天机阁定义自己的逻辑架构和契约。外部运行平台只是部署适配目标，不拥有天机阁的治理语义。

### 6.3 外部业务与行动系统

- 企业 CRM、ERP、工单和知识系统；
- 通知、支付、交易和协作系统；
- 需要被查询、更新或触发的其他业务平台。

天机阁可以产生建议或在授权条件下调用外部能力，但外部系统的最终业务状态由对应系统拥有。是否允许直接外部行动仍属于后续治理与授权专题，不在系统上下文阶段提前收窄。

### 6.4 外部交互渠道

- Web、桌面和移动客户端；
- API；
- 邮件、短信和即时通信渠道；
- 飞书、Telegram 等协作入口；
- 语音和其他多模态终端。

渠道负责传输和呈现，天机阁负责身份解析、会话连续性、任务语义和情报产品。

### 6.5 外部权利、制度与监督生态

- 数据主体、内容与数据权利人；
- 被研究主体和受影响第三方；
- 法律、监管、司法和标准机构；
- 独立审计、认证、归档和取证主体。

这些外部主体可以约束、纠正、挑战或验证天机阁，但不因此进入天机阁内部治理机构。

### 6.6 外部开发者、同行与对抗生态

- Tool、Skill、插件和集成开发者；
- 能力市场、开源社区和依赖维护者；
- 其他情报、知识和 Agent 系统；
- 联合调查联盟和数据交换平台；
- 恶意内容发布者、投毒者、内部滥用者和被攻陷供应商。

非合作主体不需要通过正式 API 进入系统，也可能借公开内容和供应链影响认知与运行。

## 七、核心交互关系

| 外部主体或系统 | 进入天机阁 | 天机阁返回 |
|---|---|---|
| 仙人 | 目标、问题、决定、反馈、资料 | 对话、解释、产品、告警、升级请求 |
| 平台运营者 | 平台配置、能力供应、租户生命周期操作 | 平台状态、容量、质量和审计 |
| 租户系统 | 授权数据、事件、组织上下文 | 查询结果、报告、告警、受控调用 |
| 外部数据源 | 文档、记录、事件和元数据 | 请求、订阅、访问与纠错操作 |
| 模型与智能服务 | 推理、识别、转换结果 | 受策略约束的输入和调用参数 |
| 身份提供者 | 身份声明和认证结果 | 认证请求与会话绑定 |
| 人类专家 | 复核、裁定、知识和反馈 | 待审材料、证据包和决定请求 |
| 消息渠道 | 用户消息、回执和交互事件 | 回复、通知、报告和告警 |
| 权利人/被研究主体 | 更正、异议、权利与处置请求 | 受控解释、处理决定和通知 |
| 监管/司法/标准主体 | 适用规则、裁判、许可和约束 | 合规证明、报告和响应 |
| 外部开发者/同行系统 | 能力、数据交换和联合任务 | 受控调用、产品和协作状态 |
| 对抗主体 | 欺骗内容、注入、投毒和滥用 | 阻断、隔离、纠正和调查响应 |

## 八、全链路上下文包

每个需要归属和追踪的请求、任务、数据操作和模型调用都必须能够关联一个上下文包：

```text
Context Envelope
├── tenant_id
├── data_scope / collaboration_space_id
├── subject_id / actor_type
├── delegation_chain
├── emperor_identity_id
├── court_profile_version
├── mission_id / run_id / task_id
├── authorization_context / policy_set_version
├── budget_context
├── risk_context
├── evidence_requirement
├── quality_profile
├── lifecycle_context
├── trace_id / causation_id
└── time_context
```

并非所有字段在每个阶段都必须物理复制，但其语义必须可解析、可追踪且不能因跨面调用而静默丢失。

## 九、上下文不变量

- 平台共享不等于租户数据共享；
- 每个租户默认拥有独立逻辑朝廷和皇帝身份；
- 皇帝稳定身份不等于永久常驻 Agent 进程；
- Agent 实例必须加载当前租户、用户、权限、预算、风险和追踪上下文；
- 公共作用域必须显式表示，不能用缺失 `tenant_id` 暗示公共；
- 用户需求可以改变调查范围和产品表达，不能改变公共事实的来源、身份和验证状态；
- 外部模型、数据源和运行平台不拥有天机阁的治理语义；
- 天机阁对外部结果承担验证和使用责任，不把供应商输出直接当作事实；
- 外部行动能力是否启用不改变天机阁内部必须可追踪、可治理的原则；
- 皇帝、Agent 和内部服务只拥有派生、限域、限时且可撤销的权力；
- 事实接受、数据使用、产品消费与外部行动属于不同权威域；
- 被研究主体和受影响第三方即使不是用户，也必须能在生态与血缘中表示；
- 外部业务状态由对应系统及责任主体拥有，调用成功不等于现实结果成立；
- 系统上下文只划分责任所有权，不以当前技术能力限制未来功能范围。

## 十、显式未完成项

系统上下文已经确定主体和边界，但以下内容留给后续骨架闭合步骤：

- 角色与授权矩阵；
- 跨租户会盟和临时联合调查空间；
- Court Profile 的完整 Schema 和版本状态机；
- 皇帝身份、人格、记忆和运行实例的精确关系模型；
- 外部行动的批准、补偿和责任机制；
- 外部来源与模型的信任分级；
- 核心对象的完整 Schema 及跨边界协议细节；第一版对象主干已经建立。
