# 天机阁七条全局流骨架

状态：Accepted

生效日期：2026-07-24

## 一、骨架定位

天机阁此前的总图经常用一条箭头同时表示命令、数据搬运、知识形成、授权、预算、审计和反馈。这会掩盖权力方向、数据所有权和回流关系。

本轮把七种语义拆开阅读：

1. 控制流；
2. 数据流；
3. 知识形成流；
4. 决定与授权流；
5. 预算与资源流；
6. 审计与证据流；
7. 反馈与演进流。

它们不是七套系统，也不是新增一级面。一项任务通常同时穿过多条流。

## 二、控制流

控制流回答：“谁要求系统改变行为或状态？”

```text
仙人 / 平台制度 / 租户制度 / 世界触发
→ 人机交互或平台控制
→ 智能治理形成 Mission、Plan、Decision
→ 智能执行与运行编排 Run / Task
→ 领域、认知、研判、产品能力执行
→ 实际状态回报治理与平台控制
```

控制流向执行方向下发目标和决定，向上返回实际状态、异常和完成情况。数据底座可以保存控制记录，但不因保存它们而拥有治理权。

## 三、数据流

数据流回答：“原始内容、记录和计算结果移动到哪里？”

```text
外部来源 / 租户资料 / 业务系统
→ 接入、采集、上传或订阅
→ 原始 Document / Snapshot
→ 解析、清洗、去重和结构化 Artifact
→ 数据底座中的对象、索引和版本
→ 检索、分析、产品和受控外部输出
```

数据流描述载荷和副本，不表示内容已经可信。Document 移动到认知处理位置，不等于它已经成为 Evidence 或 Fact。

## 四、知识形成流

知识形成流回答：“信息如何获得越来越强的语义？”

```text
Source / Document / Snapshot
→ Evidence
→ Claim
→ Verification
→ Fact / Disputed Claim
→ Entity / Relationship / Event / Change
→ Signal / Assessment
→ Forecast / Risk / Recommendation
→ Intelligence Product / Alert
```

知识流创建新对象和血缘，不是把同一份数据原地改名。它可以反向要求补证、重新关联、纠正或重评。

## 五、决定与授权流

决定与授权流回答：“某主体为什么有权看到、决定或执行？”

```text
法律/权利/平台/租户/人类权威
→ 身份、角色、策略、数据许可和委托
→ 当前 Mission 与作用域
→ 各边界的允许 / 拒绝 / 附条件允许
→ 执行、读取、发布或外部行动
→ 撤销、到期、复核和责任追踪
```

授权流与控制流不同：收到 Command 不代表已经有权执行；皇帝或尚书决定“做什么”，不能替代数据、工具和外部行动的适用授权。

## 六、预算与资源流

预算流回答：“资源从哪里分配、由谁消耗并如何回收？”

```text
平台容量与租户配额
→ Mission 预算
→ Run 预留与 Task 分配
→ 模型 / Tool / 计算 / 存储 / 人类资源消耗
→ 计量、结算与释放
→ 成本偏差、预算压力和重新规划
```

预算流约束控制流，但不能取代它。资源充足不产生授权，资源不足也不能取消安全、证据和审计底线。

## 七、审计与证据流

审计流回答：“系统如何证明发生过什么以及为何发生？”

```text
Intent / Decision / Command / Read / Write / Invocation / Publication
→ trace、因果、主体、策略和版本记录
→ 数据底座中的审计、血缘与决定记录
→ 都察院、平台治理、人类或外部监督复核
→ 异常、纠正、问责和改进信号
```

审计记录观察其他流，不自动成为新的业务命令。审计发现的问题要通过控制流或授权流形成有权处置。

## 八、反馈与演进流

反馈流回答：“结果如何反过来改变目标、知识、产品和系统能力？”

```text
用户反馈 / 现实结果 / 新证据 / 预测评分
+ 质量 / 成本 / 失败 / 供应商与时代变化
→ Feedback / Evolution Evidence
→ 目标修正、事实纠正、研判校准、产品改进
→ 能力缺口、候选、实验和评测
→ 智能治理审核
→ 平台控制发布或回滚
→ 新一轮运行
```

反馈不能直接静默改写事实或生产能力；它必须重新进入相应的知识、控制和演进路径。

## 九、七流—十面主关系

| 一级面 | 主要产生或主导的流 | 主要接受的流 |
|---|---|---|
| 人机交互 | 控制入口、反馈、交付数据 | 产品、决定、授权结果 |
| 情报产品 | 产品数据、交付、使用反馈 | 知识、授权、发布控制 |
| 数据认知 | 知识形成、数据加工反馈 | 原始数据、任务控制、领域语义 |
| 情报研判 | 知识形成、风险与补证反馈 | 事实、目标、领域知识 |
| 智能治理 | 控制、决定、审核反馈 | 意图、状态、证据、授权和预算约束 |
| 领域能力 | 领域知识与能力反馈 | 领域任务、共享对象 |
| 智能执行与运行 | 执行控制、资源计量、运行审计 | Plan、授权、预算和期望状态 |
| 数据底座 | 数据供应、血缘与审计读取 | 所有需持久化的数据和记录 |
| 平台控制 | 平台控制、授权政策、预算分配 | 治理决定、实际状态、演进结果 |
| 能力演进 | 反馈与演进 | 质量、成本、失败和时代变化 |

一张矩阵只能说明主关系；具体交互仍由跨面契约表达。

## 十、关键交叉关系

```text
控制流必须受授权流和预算流约束
数据流必须携带作用域并产生审计流
知识流必须引用数据流中的原件与版本
产品交付同时属于数据流、知识流和授权流
外部行动同时需要控制流、授权流和审计流
反馈流通过治理后才能改变控制流
演进流通过发布决定后才能改变生产期望状态
```

## 十一、骨架级不变量

- 同一条箭头必须声明主要语义，不能同时冒充七种流；
- 控制权、数据所有权、事实接受权和存储所有权相互分离；
- 数据到达不等于知识成立；
- Command 到达不等于授权成立；
- 预算可用不等于动作被允许；
- 审计发现不等于处罚或修正已经获批；
- Feedback 不得直接覆盖事实、研判或生产版本；
- 任一重要结果都应能从七条流中解释其目标、载荷、知识、权力、资源、记录和回流。

## 十二、当前刻意不展开

- API、事件、消息与文件协议；
- 数据格式、Schema 和字段；
- 身份与授权算法；
- 计费、配额和资源调度算法；
- 审计存储与查询实现；
- 反馈学习算法和自动化阈值；
- 物理网络、区域和部署路径。
