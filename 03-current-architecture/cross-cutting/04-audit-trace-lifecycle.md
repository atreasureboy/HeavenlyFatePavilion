# 审计、追踪与数据生命周期

状态：Accepted

## 一、三类记录不可混同

```text
Operational Telemetry
指标、日志、追踪，用于运行诊断，可采样并按运维周期保留

Decision / Provenance Record
输入、版本、证据、推理产物和决定，用于复现与纠正

Audit Record
谁在何种权限和上下文下做了什么，用于责任与合规证明
```

可观测日志不能代替审计；审计也不应承担所有高吞吐调试细节。

## 二、端到端追踪

追踪链以 `trace_id` 关联，以 `causation_id` 表达因果：

```text
Intent
→ Mission Decision
→ Plan / Run / Task
→ Agent / Tool / Model Invocation
→ Data Read / Write
→ Claim / Fact / Assessment Transition
→ Product / Alert Publication
→ Feedback / Correction / Evolution
```

每个关键决定至少记录：

- 决定主体和代表关系；
- 输入对象及版本；
- 适用策略及版本；
- 授权和预算引用；
- 证据、风险与质量上下文；
- 决定、理由和备选；
- 发生时间和因果链；
- 后续副作用或补偿引用。

## 三、审计强制点

以下动作必须先确保审计可记录：

- 权限、角色、Court Profile 和政策变更；
- 私有或敏感数据访问；
- Tool、模型和外部系统调用；
- Fact 接受、争议、撤回和覆盖；
- 高影响研判、预测、风险与发布决定；
- 产品分发、告警升级和外部动作；
- 预算追加、豁免与人工接管；
- 能力版本发布、回滚和评测数据使用；
- 数据导出、保留冻结和删除。

审计存储由数据底座承载，业务主体只能追加有权限的解释或纠正，不能静默覆盖历史。

## 四、数据生命周期

对象生命周期由业务状态和数据处置状态两个正交维度组成：

```text
业务状态：Draft / Active / Disputed / Superseded / ...
处置状态：Hot / Warm / Cold / Archived / Held / DeletionPending / Deleted
```

处置策略至少由以下条件计算：

```text
对象类别
+ 数据分类和敏感度
+ 作用域与所有者
+ 来源许可
+ 地域驻留
+ 租户政策
+ 法定/合同保留
+ 证据与审计依赖
+ Legal Hold
= Retention and Disposition Policy
```

删除不是单表删除，而是对原件、副本、索引、向量、缓存、派生数据、产品引用和备份的可证明处置流程。

## 五、删除与纠错

```text
Deletion Request
→ 身份、范围和合法性验证
→ 依赖与 Legal Hold 分析
→ 批准 / 拒绝 / 延期决定
→ 阻止新的非必要使用
→ 分层执行删除、匿名化或隔离
→ 重建索引与缓存
→ 标记受影响派生对象
→ 形成处置证明
```

需要保留审计证明时，可以保留最小不可逆凭据，不保留被请求删除的业务内容。

纠错保留历史版本与替代关系；删除按政策使内容不可再用。二者不能混成同一操作。

## 六、不变量

- 高影响状态变化必须有可追溯决定。
- 任何一级面都不能自行关闭全局审计。
- trace 断裂时不得把结果包装成完整可复现产品。
- 业务终态不等于数据立即删除。
- Legal Hold 阻止处置，不赋予新的读取和业务使用权限。
- 删除必须覆盖搜索、向量、缓存和派生使用路径。
- 审计记录自身也受访问控制、保留、地域和最小化约束。

## 七、异常路径

```text
审计写入失败   → QLT → 高影响动作停止，低风险只读显式降级
trace 断裂     → QLT → 隔离结果并补链，不能发布为完整产品
保留策略冲突   → POL → 平台策略裁定，默认采用更严格处置
删除不完整     → S3 → 隔离对象、重复扫描并生成补偿任务
Legal Hold 冲突→ Deferred → 保留处置请求和理由，等待解除
审计篡改迹象   → S4 → 冻结相关记录、独立调查和人类接管
```
